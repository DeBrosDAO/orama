# E0 spike: a private Tor network

**Date:** 2026-10-09. **Branch:** `nightly`. **Status of the spike: a desk spike. No tor process was started.** This file
says what was established, what was only written down from Tor's documentation, and what the first stagenet
bring-up must confirm. The owner has not signed off; do not mark E0 done from this file alone.

**Why no live run.** The machine this was written on has no `tor`, `tor-gencert`, `sbws` or `arti`, and its Docker
daemon was not running. Installing them means downloading from package repositories, which was not authorised for
this task. Nothing here was measured. Where the spec asks for a measurement (consensus time, sbws behaviour, arti
embedding), the answer below is "not measured" with the procedure that will measure it.

The spike did not change production behaviour: the code it produced (`core/pkg/tornet`) is called only by the E1-E4
installer path, which is opt-in per node (`--services dirauth|relay|exit|onion`).

## The seven questions

### 1. A production-grade private network (3 authorities, relays, an exit, a client; `TestingTorNetwork 0`)

**Settings chosen** (all in `tornet.RelayTorrc`/`ClientTorrc`/`OnionTorrc`; `TestingTorNetwork` is never set):

- `DirAuthority <nick> orport=<p> v3ident=<hex> <ip>:<dirport> <rsa fingerprint>` for each authority, in every role.
  This replaces Tor's built-in authorities; `UseDefaultFallbackDirs 0` is set beside it so no node of the network asks
  the public network's directories for anything.
- Authorities: `AuthoritativeDirectory 1`, `V3AuthoritativeDirectory 1`, the voting schedule
  (`V3AuthVotingInterval`, `V3AuthVoteDelay`, `V3AuthDistDelay`), `AuthDirMaxServersPerAddr 1`. The schedule is in the
  network file because all authorities must agree on it. Checked at install the way Tor checks at startup: the interval
  divides 24 hours, delays at least 20 s, `2 x (vote + dist)` under the interval.
- **Bootstrap.** A network with no consensus cannot test its own reachability. `bootstrap: true` in the network file
  sets `AssumeReachable 1` on authorities and relays (the manual's wording: "used when bootstrapping a new Tor
  network"). That also makes authorities list every connected relay untested, so it is switched off after the first
  consensus. What chutney skips and a production network needs: `bootstrap` off afterwards, real timings (no
  `Testing*` intervals), real reachability tests, `Address` set explicitly for a node behind NAT (the co-located
  namespace), the HSDir uptime (below) and the subnet rule (below).
- **HSDir flag.** Tor's default `MinUptimeHidServDirectoryV2` is 96 hours: for the first four days of a new network no
  relay is an HSDir, so a v3 onion service cannot publish its descriptor. The network file's
  `hsdir_min_uptime_hours` writes the option on authorities. Written from the manual; the option name is the one
  thing here most worth checking first (a wrong name makes the authority refuse to start, which is loud).
- **Subnets.** Tor never puts two relays of one /16 in a circuit (`EnforceDistinctSubnets`). Stagenet has five relays
  in two /16 networks, so no 3-hop circuit through the exit exists. `allow_shared_subnets` writes
  `EnforceDistinctSubnets 0` in every role.
- Consensus method: nothing to configure; the authorities choose the highest method they all support.

**Measured time to a usable consensus: not measured.** Expected by reading dir-spec: the first consensus appears at
the next voting-interval boundary after at least a majority of authorities have uploaded descriptors, plus the vote
and distribution delays: under one interval plus about ten minutes (about 40 minutes with the stagenet schedule). A
relay is listed once an authority has tested its ORPort. Measure it at stagenet bring-up: `orama global tor info`
prints the consensus validity, and the journal of the authority has the vote and consensus lines.

### 2. Bandwidth measurement (sbws)

**Not run.** Written from sbws's documentation as remembered, unverified: sbws needs a Tor client, a destination web
server that serves a large file over HTTPS, and a set of relays to measure through; it writes a bandwidth file the
authorities read through `V3BandwidthsFile` (the renderer supports the option). Not known: the minimum relay count
sbws needs on a network this small, and how easily a relay games a measurement (a relay that can recognise the
destination or the measurement circuits can favour them). What exists in the code instead: with no bandwidth file the
authorities weight relays by what they report, so **consensus weight must not pay anyone** until sbws runs. The
`orama-global-sbws` and `orama-global-reporter` unit renderers are old placeholders with no installer.

### 3. arti as a client

**Not run.** Believed, unverified: arti has configuration for its own authorities and fallback caches
(`tor_network` in its config), is a Rust crate and so can be embedded in a Tauri app, and the Tor Project's
`onionmasq` is the Rust layer under its mobile VPN work. None of it was tried. The VPN app (E6) is on the
Track E-clients branch and must settle this against the real arti version before it commits to it; the network file
and `tornet.ClientTorrc` are the C tor client's side of the same configuration.

### 4. Relay families

`MyFamily` is what the renderer writes (`--tor-family`, RSA fingerprints). Whether the pinned Tor version also supports
the newer family keys (relay family ids) depends on the version deb.torproject.org ships when this is installed: **not
checked**. Families are mutual: each relay of an operator must list the others.

### 5. Relay keys

- A relay is named by its RSA identity digest (SHA-1 of the DER RSAPublicKey of `keys/secret_id_key`), which is what the
  consensus `r` line, a `DirAuthority` line and a descriptor carry. `tornet.RelayFingerprint` computes it from the key
  file and the ceremony checks it against what tor prints.
- The ed25519 identity is the master key `keys/ed25519_master_id_public_key` (32-byte header then the key). A vote
  carries `id ed25519 <base64>` per relay: that is the RSA-to-ed25519 mapping the authorities certify, and it is what
  C8 and E5 should read (the vote fixture has the line). The cross-certification inside descriptors
  (`identity-ed25519`, `rsa-crosscert`) is not parsed by anything here.
- **Can tor sign an arbitrary message with its ed25519 identity?** Not through anything tor exposes. The master secret
  is a file holding an *expanded* key (a 64-byte secret after the header), which Go's `crypto/ed25519` cannot sign with;
  signing with it means implementing expanded-key signing ourselves (B4), and with `OfflineMasterKey 1` the master
  secret is not on the host at all. Not tried. The ceremony keeps the master key with the other relay keys on the
  authority host (stagenet), which an authority operator on mainnet would change.

### 6. Sybil controls on the authorities

Set: `AuthDirMaxServersPerAddr 1`. Available in Tor and not wired: `AuthDirReject`, `AuthDirInvalid`, `AuthDirBadExit`
(by address) and the `approved-routers` fingerprint list (`!reject`, `!invalid`, `!badexit`), from the manual,
unverified here. The Guard, Stable, Fast and HSDir thresholds are not torrc options: each authority computes them
from the network and writes them in its vote (`flag-thresholds`). So "reachability and uptime requirements before a
relay earns Guard" are relative to the network and can be read from the first real vote, not configured. Operators are
self-declared, so bonds (C8) are the real control; none is wired.

### 7. Fixtures

Synthetic ones exist (above). Real ones come from the first archive. The archive's layout, manifest and root are what
E5's `inputs_root` commits to.

## What the stagenet bring-up must confirm

Everything here was written without running tor. In the order a run finds them, with what shows each:

1. **Tor accepts every directive.** Start each unit and read its journal for `Unknown option` / `Failed to parse`.
   The directives written from the manual and not seen to work: `MinUptimeHidServDirectoryV2`, `AuthDirMaxServersPerAddr`,
   `ORPort <p> IPv4Only`, `HiddenServiceEnableIntroDoSDefense`, `HiddenServiceMaxStreams`,
   `HiddenServiceMaxStreamsCloseCircuit`, `EnforceDistinctSubnets`, `RelayBandwidthRate ... Mbits`, the `DirAuthority` line with a
   40-digit fingerprint and no spaces.
2. **The ceremony's tool calls.** `tor-gencert --create-identity-key --passphrase-fd 0` takes the passphrase from stdin
   without a trailing newline; `tor --list-fingerprint ... --ORPort <p>` makes `keys/secret_id_key` and the ed25519
   master files and prints `nickname fingerprint`; the certificate has `fingerprint` and `dir-key-expires` lines.
   (`TestCeremony_realTorMakesKeysTheNetworkFileNames` runs this on a node with the real binaries.)
3. **`v3-status-votes`** in an authority's DataDirectory holds the votes of the current round, concatenated; the archive
   reads that file and `cached-consensus`. If either is somewhere else, `orama global tor archive` will say it holds no
   consensus or archive without votes (`votes_missing`).
4. **The sandbox lets tor run**: `AF_NETLINK` for interface listing, `SystemCallFilter=@system-service`
   minus `@privileged @resources` with `EPERM` on a refused call, `MemoryDenyWriteExecute`, `IPAddressDeny` of private
   ranges, inside the `orama-global` namespace. A tor that logs permission errors on `setrlimit` or `getifaddrs`
   needs the unit adjusted in the renderer, not on the node.
5. **`Address` behind the namespace's DNAT** is accepted and reachability tests from the other authorities succeed
   (`TestRelays_orPortIsReachableAndTheGateIsNot`; the relay appears in the consensus).
6. **A consensus appears** and every relay is listed `Running` (`TestAuthorities_signAConsensusThatListsEveryRelay`).
   Note the time from the first start to the first fresh consensus: that is the number item 1 asks for.
7. **Guard and HSDir flags exist** after the first hours (the `s` lines of the consensus), or circuits and the onion
   service cannot be built. If they do not, read `flag-thresholds` in a vote before changing anything.
8. **Circuits and the onion service**: a client of the network built only from `tor-network.json` bootstraps,
   builds 3-hop circuits, reaches the onion address and an exit fetch
   (`TestNetwork_circuitsAndOnionServicesWorkThroughOurAuthorities`, `TestExit_leavesFromTheNodeAndRefusesWhatItShould`).
9. **Leave bootstrap**: set `bootstrap` false, re-install, restart one node at a time, and check the consensus stays fresh. A relay behind the
   co-located namespace's DNAT tests its own reachability by a circuit that ends at its public address from another relay, which arrives
   through the host's DNAT like any inbound connection (no hairpin); if the journal still says the ORPort is unreachable, that is the
   first thing to look at.
10. **AppArmor.** The Tor Project's package may ship a profile for `/usr/bin/tor`. The existing client (`/var/lib/orama-tor`) runs, but the new
    state directories (`/var/lib/orama-global/tor-*`) and the new accounts have not been tried under an enforcing profile: `aa-status`, and
    `journalctl -k | grep DENIED` after the first start.
11. **Directive names the reviewers could not check without running tor** are listed in item 1; a unit that fails to start names the one.

## Decisions taken (E1) and why

| Decision | Value | Reason |
|---|---|---|
| Network id on stagenet | `orama-stagenet` | the product name (P8) is not decided; the id is only a label in the file |
| Voting schedule | 30 min interval, 300 s vote delay, 300 s dist delay (stagenet); the ceremony's default is 60 min | a short interval makes the first consensus come sooner and a restarted authority recover sooner; 60 minutes is Tor's own |
| Signing certificate | 12 months, rotated by hand with `tor-gencert --reuse` before month 12 | the spec; no alerting yet |
| Authorities on stagenet | mew, mewtwo, gengar (three of the five machines, two providers) | no separate machines exist; the plan wants separate machines in three jurisdictions (a stated deviation, owner to confirm) |
| Exit on stagenet | froakie only, opt-in (`relay,exit`) | owner approved a real open exit; one exit keeps the complaint surface to one address; the choice of machine is the owner's |
| `allow_exit` in the network file | true on stagenet only | an exit is a property of the network, not just a flag a node's operator can pass |
| Exit policy | reserved ranges, mail (25, 465, 587), Tor's default file-sharing ports, accept the rest; IPv4 only | the spec's "no SMTP 25", plus the ranges that include the co-located host's veth address |
| Sybil control | one relay per address | the manual's default is two; a host runs one relay |
| Ports | ORPort 31020, DirPort 31021 (already reserved), tx gate 31022 loopback, client SOCKS 9052 | 9051 is the old Anyone ControlPort the firewall reconciler still closes |
