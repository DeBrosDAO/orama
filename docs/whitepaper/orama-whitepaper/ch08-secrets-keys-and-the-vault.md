# Secrets, keys and the vault

> **At a glance.**
>
> - **What:** three kinds of key material: shared roots the genesis node generates, keys derived from them with HKDF-SHA256 and a purpose label, and keys generated where they are used. Stored secrets are sealed with AES-256-GCM under an encryption root that can be rotated without touching the mesh. Separately, the vault keeps small client-encrypted blobs as Shamir shares, one per node.
> - **Key numbers:** 12-byte random nonces, 32-byte HKDF outputs, envelopes `enc:` and `enc:v1:<keyid>:`; signing-key overlap 15 min on rotation; vault guardian on port 10106 of the WireGuard address; read threshold K = max(2, floor(N/3)), write quorum W = min(N, max(K+1, ceil(2N/3))); share at most 512 KiB; challenge 60 s, session 1 h, pull skew 120 s; fan-out budget 15 s.
> - **Code:** `core/pkg/secrets/`, `core/pkg/secrets/root.go:LoadOrMaterialize`, `core/pkg/gateway/secrets_rotate.go:handleRotateSecrets`, `core/pkg/shamir/shamir.go:WriteQuorum`, `core/pkg/gateway/handlers/vault/`, `vault/src/`.

## The problem

A cluster holds tenant secrets (function secrets, push credentials, deployment environments), credentials the nodes use with each other, keys that sign what clients see, and keys that identify machines. Four constraints shaped how they are kept.

Every node must compute the same key without asking anybody: there is no key service and no leader that hands out keys at run time. The first design generated a key file per node and diverged, so a function secret written on one node could not be read on another. Deriving keys from one shared value fixed it.

Stored secrets must be rotatable. They were encrypted under keys derived from the cluster secret, which is also IPFS Cluster's private-network key and the root of every inter-node MAC. Rotating it partitions the cluster, so in practice it was never rotated.

Upgrades are rolling and mixed-version, so a new binary must not write a format an old one cannot read.

Some keys must not be shared at all. A signing key derived from the cluster secret is held by every node and every compromised tenant gateway.

## Three families of key

**Shared roots** are 32 random bytes in 64 hex characters, generated at genesis and copied to every joiner in one response over an invite-authenticated, certificate-pinned connection: the cluster secret, the IPFS swarm key, the RQLite password, the API-key HMAC secret and the TURN secret. Each file is mode 0600. A file of the wrong length is regenerated by the installer, but the encryption-root loader never regenerates anything it cannot read, because a silent replacement orphans every stored secret.

**Derived keys** are `HKDF-SHA256(root, salt = nil, info = purpose)`. The purpose label is a domain separator, so a MAC made for one consumer never verifies for another, and every consumer gets its own label: the coordination key, the hop key, Caddy's ACME key, the IPFS credentials and the per-namespace capability keys. A nil salt is kept because adding one would change every key; it belongs inside a rotation. Every site trims the secret first, since a trailing newline on one node's copy would derive a different key and fail every call with no visible reason.

**Local keys** are generated where they are used and never leave: gateway signing keys, node keys, WireGuard keys and the libp2p identity. Only public halves are published.

## The encryption root

Stored ciphertext is keyed from the encryption root, whose generation 1 is a byte-for-byte copy of the cluster secret, so nothing is re-encrypted at upgrade. Each rotation creates the next generation from 32 fresh random bytes. A keyset opens a versioned envelope with the key whose id matches and a legacy envelope with the current key, then the previous, so rows stay readable during a rotation.

The registry table `encryption_roots` is the truth. Each gateway caches the root in its own state directory, and a seed from install sits in the node's `secrets/`. `LoadOrMaterialize` runs at gateway boot and asks the registry first; any registry error other than "no row yet" is returned, because a root read from a file while the registry cannot be asked may predate a rotation. A gateway that cannot load the root does not start. It used to fall back to the cluster secret, which on a rotated cluster is the wrong key, so everything it then wrote was unreadable to the others. The table sits in the cluster registry on purpose, and the tenant SQL guard denies it, since a tenant copy would be a key-encryption key the tenant could rewrite.

The legacy envelope `enc:` stays the default write until an operator runs the format rewrite after every gateway is upgraded. Decryption fails closed: an unprefixed value, an unknown key id or an unreadable root file is an error.

## Rotation

`orama operator rotate-secrets` has two modes. Without `--rotate` it switches the cluster to versioned writes under the same root. With `--rotate` it creates the next generation. Either way the handler (`handleRotateSecrets`) swaps the new root into the gateway, then runs the walker, which reads every sealed column from a fixed list (agent tokens, deployment environments, function secrets, push tokens, TURN secrets), decrypts, re-seals under the current key and writes the row back. A row that fails is recorded and left alone. The walk is idempotent because rows already on target are skipped. An index gateway then pushes the whole root to each namespace gateway in turn, with a coordination v2 stamp whose audience is that node and a 60 s timeout.

A receiving gateway writes the new root to its own cache before using it, so a crash cannot leave it on a root it could not reload. `CheckSuccessor` refuses a pushed root with a lower generation, or an equal generation with a different key, so a captured push cannot be replayed after a later rotation.

Signing-key rotation orders its steps so every failure leaves a consistent state: write the private key, publish the public key (restoring the old private key if that fails), switch signing, then retire the previous key 15 minutes later so no token already issued stops working. Rotation is local to the gateway that answered.

## What a compromised gateway holds

Every tenant gateway unit gets the cluster secret and the encryption root bound into an otherwise empty tmpfs, because it needs them to verify hops and derive capability keys. Code execution in one tenant's gateway therefore yields the root and every key derived from it. At-rest encryption protects snapshots, backups, disk images and a stolen database file, not a compromised gateway. A registry snapshot is the most sensitive artifact in the cluster: `encryption_roots.ikm` is stored in plaintext beside the data it seals. Most shared roots have no rotation path, and removing a node rotates none of them.

## The vault

A wallet client needs somewhere to keep an encrypted backup of its key material, such that losing the device does not lose the wallet and no operator can read it. The vault stores that blob as Shamir shares over GF(2^8) with the AES polynomial. Fewer than K shares are statistically independent of the secret, whatever the attacker's compute.

![Vault overview: gateway split and combine, guardians on the overlay](../technical-reference/diagrams/ch28-overview.svg)

Every node runs a `vault-guardian` (Zig, a static musl binary) on port 10106 of its WireGuard address. A guardian only receives a share, checks who sent it and writes bytes. Every active node holds one share of every secret, so the guardian set is the fleet and there is no placement logic. Applications cannot reach the overlay, so the gateway's `/v1/vault/push` and `/v1/vault/pull` split and combine in the gateway's own memory. By design the envelope is ciphertext produced by the client, so the gateway handles an encrypted blob and never the key.

K is the read threshold and W the write quorum. With three guardians, K = 2 and W = 3: one stopped guardian refuses every write while reads survive. W exceeds K so that a write reported stored is always recoverable. The earlier formula gave W = 2 and K = 3 at N = 3, so a push could succeed while storing too few shares for any read, with nothing at write time to say so. V1 stores K beside the share, so fleet growth does not change how existing secrets are read.

Identity is the SHA-256 of an Ed25519 public key; there is no registration. Every push and pull carries the key and a signature over a domain-separated message, binding the version (push) or a timestamp within 120 s (pull). The gateway verifies it, then each guardian verifies it again, so guardians do not trust the gateway for authorization. The guardian's own HMAC session (60 s challenge, 1 h token) proves only that the caller reached it, so the gateway repeats the handshake with each guardian on each request: three requests per guardian per operation.

The order of the push matters. A per-source-address limiter runs before signature verification, because a guesser who mints a valid signature for every guessed seed would never trip a limit that counted only authenticated requests. A per-identity limiter runs after, so a third party cannot drain a victim's budget. Then the gateway fans out under a 15 s budget, 5 s per guardian. Acks at least W is a 200; conflicts at least W is a 409; anything else is a 503, which does not mean nothing was written. On a pull, the gateway groups shares by version and combines only the first K of the newest version with enough shares. Shamir cannot detect mixed or too few shares, so combining across versions would return a wrong secret with no error.

A guardian writes `share.bin`, then `checksum.bin`, then `meta.json`, each by temporary file and rename, with no fsync. The checksum is an HMAC under a node-local `integrity.key`: it detects corruption, not tampering by anyone who can write the directory.

The largest limit is that the guardians do not know about each other. Peer discovery, repair and proactive re-sharing exist in the Zig tree but are not linked into the daemon, so a guardian that joins holds nothing for existing secrets and a guardian that leaves takes its shares until the owner pushes a new version.
