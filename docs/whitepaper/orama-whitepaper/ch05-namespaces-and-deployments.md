# Namespaces and deployments

> **At a glance.**
>
> - **What:** a namespace is the unit of tenancy: creating one provisions a private RQLite, Olric and gateway on each of three nodes, registers the cluster, publishes DNS and proves it serves before calling it ready. A deployment is a tenant's application: a static site served from IPFS, or a process in its own sandboxed systemd unit on a home node and one replica.
> - **Key numbers:** 3 members per namespace (1 on a one-node fleet, a two-node fleet refused); 5-port blocks in 10000 to 10099, at most 20 per node; provisioning bound 5 min, per-service readiness 60 s; per-wallet cap 10 namespaces; deployment ports 10200 to 19999; 2 replicas; health probe every 30 s, restart after 3 misses; update handler budget 330 s.
> - **Code:** `core/pkg/namespace/blueprint.go:BlueprintTenantN`, `core/pkg/namespace/port_allocator.go:AllocatePortBlock`, `core/pkg/deployments/process/manager.go:Start`, `core/systemd/orama-deploy-go@.service`, `core/pkg/gateway/handlers/deployments/update_handler.go:HandleUpdate`, `core/pkg/deployments/health/orphan_reaper.go:reapOrphanUnits`.

## A tenant is a small cluster

The first design commitment is that tenants share no data layer: no process, database file or Raft group of one tenant's data is also another's. That turns every namespace into a small distributed system created on demand on a few VPS machines with no container runtime, and the code solves what a scheduler normally would.

Placement must not let two creations take the last free slot. Port assignment must record every block, because a port handed to a second namespace while the first one's process still holds it makes the second join the first one's Raft group. Readiness must mean the three services work together, not that systemd exec'd them. Removal must leave nothing an upgrade, a reboot or a later namespace of the same name would resurrect.

The recipe is a blueprint: three services started in order, on five consecutive ports (RQLite HTTP and Raft, Olric client and memberlist, gateway). `BlueprintTenantN` builds it for N members, and the fleet size picks N: three or more nodes give 3 (a ten-node fleet still provisions 3), one node gives an evaluation namespace with a single member, two nodes are refused (an even Raft group is a split-brain risk), and counting is of registered nodes, not live ones, so a full five-node fleet with one free slot cannot silently put all three roles on one machine.

## Creating one

`POST /v1/namespaces` takes a wallet token and runs its checks before writing anything: a name of 2 to 40 characters that is not reserved; a creation policy (operators only by default, an allowlist, or open) read before the existence check, so a wallet that is not allowed cannot learn whether a name is taken; no node still owed a teardown for that name; and a per-wallet cap of 10. The owner grant is written by one statement that counts the wallet's existing grants in its own `WHERE`, so the cap holds under concurrent creates because Raft applies one statement at a time. The handler answers 202 with a cluster id to poll.

**Placement.** The selector takes active nodes seen within two minutes with a free slot and scores them by weighted utilisation (deployments 0.30, namespace instances 0.25, ports, memory and CPU 0.15 each). It ignores latency, region and failure domain. `AllocatePortBlock` is the only allocator: it returns an existing block for the same cluster and node, which makes retries after an ambiguous failure safe; otherwise it takes the first gap and inserts, with two unique constraints (no overlap, one block per pair) arbitrating races and up to ten retries. If a node fills up under the selection, placement gives back its blocks and selects again, up to five times.

**Provisioning** runs asynchronously under a five-minute bound. The row is inserted as `provisioning` with a timestamp the registry stamps, so staleness is judged on one clock. Then for each service in order, all members spawn and are probed before the next service starts. The probes check behaviour: RQLite is `Leader` or `Follower` and answers `SELECT 1`; Olric answers a cluster client's stats call; the gateway's health reports every dependency up. The gateway probe is the first moment the three are known to work together, since only the gateway talks to both. A probe attempt times out at 3 seconds, repeats each second, and gives up after 60.

A remote member is spawned by a signed request to its index gateway over the overlay. The request carries a coordination MAC whose audience is the target's node id, a single-use nonce and a 60-second skew window, so a stamped request captured on its way to one node cannot act on another. The receiver validates every field that becomes a directory name or part of a `sh -c` unit script, and substitutes its own registry connection rather than trust the sender's. Units start through the privileged helper from env files in a root-owned tree.

DNS follows: two A records per member (`ns-<name>` and its wildcard), TTL 60 s. Creation is additive and never deletes the name first, and disabling one IP carries a guard inside the same `UPDATE` that refuses to disable the last active record. A final health verification, status `ready`, and a `cluster-state.json` written on every member complete it. That file lets a node restart its tenants with no registry, so a cold start does not deadlock; before acting on it, the node checks that the registry still assigns it that cluster, so a node replaced during downtime does not resurrect.

**Failure.** A failed spawn, readiness or DNS step rolls back on a fresh three-minute context: teardown on every selected node, ports freed only for nodes that confirmed, DNS and membership withdrawn, then `failed`. If the process dies mid-provisioning, any node's sweep fails the cluster after 11 minutes by a guarded `UPDATE` judged on the registry's clock.

**Deletion** claims the cluster with a stamped lease so two deletes cannot run, tears down on every active member at once, and records any stop a node did not confirm as an owed teardown. A teardown, not a stop, because a stopped unit stays enabled and `orama node upgrade` would restart it. Unconfirmed nodes keep their port blocks reserved, and the name cannot be created again until the debt clears.

## Deployments

A tenant also needs somewhere to run the code that talks to its database. The design starts from the fact that the code is arbitrary bytes running on the same host as RQLite, the WireGuard private key and other tenants.

A static site (or a static Next.js export) is a directory CID in IPFS that any gateway serves; it has no process and every node serves every site. A dynamic app (Next.js server, Node.js, Go binary) is one systemd instance, `orama-deploy-<runtime>@<namespace>-<name>`, on a port from 10200 to 19999. The unit declares isolation: a dynamic user and uid per deployment (derived from a hash of the instance, so one tenant cannot read a neighbour's process environment), `/opt/orama` replaced by an empty tmpfs with only the deployment's own code bound read-only, one writable state directory, no route to the overlay or any private range, and `SocketBindDeny=any` plus a per-instance drop-in that allows only its own port. The gateway is not root: every privileged step goes through the helper, and secrets are staged in a root-only tree as contents, never paths. Before every start, a root-run check confirms the code directory is a real directory owned by `orama`.

**Home node and replica.** The node whose index gateway receives the create becomes the home node for good, because it allocates the port and starts the unit. A second node is chosen by capacity and set up over the same signed overlay channel; its setup polls IPFS for the artifact, since the blocks may not have reached it yet. Deployment routes are pinned to the index gateway, since only it may drive the helper. A namespace gateway once served a delete that freed the port while a refused stop left the unit running, and the next deployment crash-looped behind it.

**Instance ownership.** Several gateways on one host share unit names, directories and files, and a name check followed by an insert is not atomic. So the host arbitrates: a create claims its instance with `os.Mkdir`, which exactly one caller wins, and writes an owner marker by hard link. Because the name-to-instance mapping is not injective, collisions are refused at create time.

**Environment and identity.** Environment values are sealed with AES-256-GCM before they reach the replicated table, are never returned by the API, and are rendered into a root-only env file with escaping read off systemd's own parser. A deployment calls its namespace as a principal of its own with a one-hour workload JWT, re-staged every 20 minutes so a crash-restart never reads an expired token.

**Changing a running app.** Update, rollback and environment changes run on the home node only (the request is proxied there, or refused with a retryable 503), under a per-deployment lock, with a monotone version stamped on every fan-out. A replica refuses an older version, so a retry that overtakes a slow call cannot overwrite a newer change. A dynamic update extracts into a staging directory, swaps, restarts and waits for the unit, and swaps back on failure. Rollback re-applies an old artifact as a new, higher version, so the counter never moves backwards. The fan-out is not best effort: if any replica did not apply the change, the request fails with 502 naming the node, since the alternative leaves two versions of the app answering one hostname. The timeouts nest, each shorter than the one around it, as in [System shape and one request](ch02-system-shape-and-one-request.md).

**Routing and health.** A request for an app host resolves the deployment by subdomain; a dynamic one is served locally on the home node's port or this node's replica port, otherwise forwarded over the overlay through a circuit breaker per deployment and node, which counts the node's failures and never the app's own 5xx. The health checker on each node probes its replicas every 30 seconds, restarts a unit after three misses, and marks a replica failed after ten restart cycles. Every 5 minutes the index RQLite leader adds replicas for deployments that have fewer than two. An orphan sweep stops units with no registry row, but only when the registry read succeeded and was non-empty, the unit was unmatched on two sweeps and is 10 minutes old, and at most two per pass.

The most important limit: a custom domain can be added and verified by a DNS TXT record, but the host-routing middleware lets every host outside the base domain through before it looks at custom domains, and the certificate check approves only the base domain, so a verified domain is neither routed nor given a certificate.
