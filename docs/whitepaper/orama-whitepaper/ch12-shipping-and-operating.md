# Shipping and operating

> **At a glance.**
>
> - **What:** how one version number becomes software on a node and stays healthy. An operator's machine builds one archive, has the operator's wallet sign its manifest, and nodes install only archives signed by an address in a root-owned list. Upgrades walk the fleet one node at a time behind a readiness gate. Nodes report their own health, operators repair what automation will not, and a three-server end-to-end suite gates releases.
> - **Key numbers:** 16 binaries per archive; one node upgraded at a time, rejoin budget 5 min, applied-index lag at most 200; node report every 10 s and stale after 90 s; recovery quiesce 60 s, kept node `Leader` within 120 s; tombstone veto 24 h; fleet suite of 87 feature packages and 1,134 tests in 11 stages.
> - **Code:** `core/pkg/archivetrust/`, `core/cmd/orama/internal/production/`, `core/pkg/rollout/`, `core/pkg/telemetry/`, `e2e/`.

## The problem

A node runs its services out of `/opt/orama/bin`, several of them holding the keys of every tenant on the machine, so whoever chooses those bytes chooses everything the node does. Upgrading is the most dangerous routine act in the system, because the registry is a Raft group that stops committing when a majority of voters is gone. And most failures that matter, such as quorum loss, mesh formation or certificate issuance through a real delegation, exist only on several servers with real DNS. The design answers each: nodes never build software, upgrades are ordered by cluster state rather than by a sleep, and the release gate runs on real servers.

## Build and signing

`/VERSION` is the only version; `make bump` writes its four copies and tests keep them equal. `orama build` cross-compiles 16 binaries and the systemd templates into one archive and lists the SHA-256 of every file in `manifest.json`. The operator's RootWallet signs the manifest with EIP-191 under a dedicated purpose, over a message that names the version, commit, architecture, date, the signer list the build would install, and the manifest's hash. That domain separation means a signature given to a login challenge can never verify as a build signature. Signing waits up to 150 s for the operator to approve in the wallet app, and the build checks its own signature with the node's verifier before writing the archive, so a signature nodes cannot verify fails the build, not every install. Third-party daemons are built from tagged source, except Kubo and RQLite, which are pinned by SHA-256 in code.

A node treats the archive as hostile until verified. Extraction accepts only regular files and directories under five owned paths, with caps of 1,024 entries, 512 MiB per file and 4 GiB in all. `VerifyTree` then checks that the signature recovers to an address in `/etc/orama/archive-signers`, that the signer list is well formed, that every directory entry is listed, and that each file matches its digest. The signature is judged before the contents, and the contents against the signed manifest, so nothing sits outside the signature. A refused archive leaves `/opt/orama` untouched.

The anchor is the one file whose integrity decides all others: root-owned, read through a no-follow descriptor, and refused if anyone but root could have written it. A genesis node seeds it from the operator's wallet after verifying the archive against that wallet. A joiner receives the cluster's list from the inviting node, checked against the signers the operator expected. A signed build may rotate the list, but it must include its own signer, and a mark holding the last rotation's build date blocks replay of an older build; retiring a key takes two builds. A second authority, the DeBros TUF release repository, signs releases with the owner's RootWallet release key (`orama maint release`: three approvals to cut a release, one to refresh the timestamp). A node that adopted its release root installs a release with no operator wallet at all; the root rotates through numbered root files that each need the previous root's signature, and a channel (nightly, main, dev/branch) is a path prefix in the one targets file. The release host and the production root ceremony are still to do. The public channel (GitHub release, apt, npm) is separate, and no node installs from it.

## Install and upgrade

`orama node install` is a fixed sequence of phases run as root: prerequisites, directory tree, binaries, Tor client, secrets, configs, templates and accounts, units, WireGuard, firewall, then verification. Verification polls four things in order (supervisor active with no restarts, RQLite `Leader` or `Follower`, `wg0` up, gateway `/health` 200) and reports the last diagnostic, not "timed out". A joining node holds a single-use invite whose hash is stored; the invite carries the inviter's certificate fingerprint, which the joiner pins, and the archive is checked before the invite is spent. The firewall reconcile never resets: it adds tagged allow rules, removes only rules it owns or that older releases are known to have added, and accepts overlay traffic only when it arrives on `wg0`, because a source address alone is not a credential.

An upgrade runs in groups. While the node still serves, it verifies the archive, resolves the public IP, records the Raft identity (id, address, suffrage), and hands over: it refuses to stop a voter unless quorum survives, transfers leadership on the index and on each tenant RQLite, and waits up to 60 s for another leader. The quorum guard counts a majority of the configured voters, not of the voters that remain, because stopping a node does not remove it from the Raft configuration. Then it stops services, swaps binaries, and re-executes itself from the new binary so config and unit generation run the new release's code. Restart waits up to 5 min for the same readiness predicate the rollout uses; tenant units start only after the index node is ready.

Two details matter in practice. Release 0.200 moved files on disk, and the migration runs inside `orama-node` as the unprivileged user: it plans every path before moving any, and refuses when both the old and new location exist. Rolling back past it is unsupported. And a release-policy library (modes off, notify and auto, a maintenance window, validators never automatic) exists but nothing runs it, so no node upgrades itself.

## Rolling upgrades

![Rolling upgrade: build, push, plan, one node at a time behind a readiness gate](../technical-reference/diagrams/ch31-overview.svg)

`orama node rollout` builds, pushes the archive to every node, and prints a plan; only `--yes` runs it. The operator's machine reads each node's Raft role over SSH and refuses to plan on an unreadable node, on two leaders (the reads straddled an election) or on none. Followers go first, sorted so the plan is reproducible, with nameservers interleaved so the zone never loses two answerers back to back, and the leader goes last. Each step runs the staged build's own CLI, since the installed one is the release being replaced.

After each step the driver polls the node every 5 s until it is `Leader` or `Follower`, names a leader, has an applied index at most 200 behind its commit index, and its gateway answers 200, within 5 min. A sleep cannot tell a node that rejoined in 20 s from one that never returned. A failed step halts the walk with the remaining nodes untouched and saves no state; the fix is to repair the node and run the same command again. Quorum arithmetic is stark: with V voters a stop needs `V/2 + 1` reachable afterwards, so three voters can roll, three with one down cannot, and a one- or two-voter index cannot be rolled at all.

Between the first push and the last restart the fleet runs two releases, and every crossing has a rule. Migrations are expand-only and applied under a cluster lock; a gateway distinguishes `starting` (no leader yet, keep retrying) from `blocked` (schema below what the binary needs, refuse) so a slow follower is not read as drift. Node-to-node MACs are written in every version and verified at the newest present, so an old signer is refused only on routes that need the new binding. A reconcile never restarts a running stateful unit because its inputs changed, which would restart three voters at once. The operator rules that code cannot enforce are to pause namespace create and delete, mint no invites, and add no nodes during the roll.

## Observability

Every node collects a JSON health report about itself every 10 s through the privileged helper, because the collectors need root and the gateway does not run as root. The cluster gateway fetches its peers' reports over WireGuard with a coordination MAC (4 s per peer, 16 in parallel), caches the assembled snapshot for 5 s and derives alerts, per-service states and one verdict. A report older than 90 s counts as unreachable, while a peer that predates telemetry is `unknown` for up to 2 h and counts for nothing, so a roll does not read as an outage. The database is judged by Raft, not by node counts, since counts cannot see quorum. Services judged are the gateway, database, cache, storage, vault, DNS and TLS, the WireGuard mesh and the chain. The public status page is a projection of service states that names no node, with 90 days of uptime recorded as one statement a minute by exactly one gateway.

`orama monitor` reads that view. `orama inspect` is a separate tool that SSHes into every node over one shared connection and runs deeper checks with pass, warn and fail bands. Its central rule is that a collection failure is not a zero: an unreachable node yields one critical result and skips its other checks, so the inspector never reports "wg0 down" from a node it could not read. Logs are zap lines in each node's journal, with no shipper.

## Recovery

The cluster heals most faults itself, so the recovery commands exist for what automation must not decide. The rule is to use the weakest mechanism that fits. A dead machine with quorum intact is `orama node remove`. Only when the registry cannot be written is it `recover-raft`.

`recover-raft` reforms the index around one node's data. It picks the node with the highest applied index, read from all nodes simultaneously, unless told otherwise. It stops every node and proves each stopped, writes a single-voter recovery file on the kept node, starts it and waits up to 120 s for `Leader` plus a strong read, wipes the other nodes only after that succeeds, and restarts followers one at a time to rejoin by snapshot. It keeps `raft.db` because the file holds the term; an earlier version deleted it and left a snapshot that every later snapshot looked older than. It deletes every other node's data and takes no backup. A cluster shrink is the same command with a smaller node list.

`remove` refuses unless every Raft group the node votes in, the platform and each namespace, keeps quorum afterwards, because retiring a node that held two of three voters of a namespace once took that namespace's writes offline. It writes a 24 h tombstone so nothing re-adds the node, then runs eight idempotent statements to release the mesh address, DNS records, slot, namespace memberships, ports and credentials, then wipes the machine. `migrate-raft-id` moves members from address ids to peer ids one node at a time and waits for each to rejoin before touching the next. `orama namespace restore` replaces a namespace database from an owner-sealed backup, but the cluster takes no backups itself. A namespace that lost quorum has no command at all: the operator writes a single-voter recovery file by hand on the surviving member.

## Testing

The layers get more expensive as they get more real. Unit tests number 8,464 in `core/`. Rule tests walk source for properties no behavioural test can see, such as the cluster secret never being compared with `==`. Where one fact lives in two modules that cannot import each other, shared JSON fixtures and byte-level vectors are read by Go, TypeScript and the live fleet, so a field renamed on one side fails a test on the other. Generated documents, such as the CLI reference and the route table, are compared with the code. `make test` runs these, the coverage gate and the book gates but not the race detector, which CI runs on the core module.

Completeness is a gate that needs no servers. The universe of 555 shipped items (232 commands, 177 routes, 59 chain messages, 64 chain queries, 23 units) must each appear under `covers:` in a feature manifest or in a waiver, and `make test` fails otherwise. The release gate is the fleet suite, run by the owner. It builds three fresh servers, installs the cluster with the real CLI through a throwaway wallet, runs 87 packages over 11 stages, collects redacted evidence and destroys everything. Requests go to the public name over TLS and logins use real signatures; SSH injects failures but never sets up state the product should. The verdict is PASS, INCOMPLETE (nothing failed but something was skipped or uncovered) or FAIL, and a failure that passes on re-run is still a failure.

The limit that matters most is that the registry has no off-cluster backup, so losing every copy of the index database is unrecoverable.
