Orama Network

A decentralized, privacy-first substrate for ordinary cloud primitives

Technical Whitepaper, First Edition  ·  September 2026
Written by members of DeBros, who remain anonymous for the same reasons this system exists.
Written against the source, which is in alpha. Where this paper and the project's documentation disagreed, the source was read and the source won.

Abstract

The commercial cloud is a single operator holding the keys to everything that runs on it. That arrangement is not incidental — visibility, control and identity all follow structurally from one company owning the machines. Self-hosting escapes it and reintroduces the operational burden the cloud removed. We describe a third position: a platform assembled from ordinary Linux services, distributed across nodes that independent operators own, and presented through one SDK and one CLI.

Orama Network implements this today. Each tenant receives a physically isolated cluster — its own consensus group, cache ring and gateway process — rather than a row prefix. All inter-node traffic crosses a WireGuard mesh that constitutes the system's single security perimeter. Authentication is a wallet signature, so no account, password or personal identifier is ever collected. Ten services are implemented and in production use by a real tenant.

We state the threat model precisely, including what it does not cover: an adversary able to snapshot the memory of a running node defeats every control described here. The engineering objective is narrower and achievable — moving secrets and plaintext out of the cheap, retroactive, offline capture path and into the expensive, targeted, live one. We report the current state without varnish, including a security audit of our own system that produced ninety findings, and we enumerate the open architectural questions that remain unresolved.

1The cloud is a landlord

The commercial cloud solved a real problem. Before it, shipping software meant buying machines, racking them and hiring someone to keep them alive. Now it means a credit card and an API call. Nobody sensible wants to go back.

But the trade that made it work has a second half that is rarely priced. In exchange for not owning the machines, you accept that one company owns them — and everything that follows. Your database sits on their disks, in a datacenter you cannot enter, under a jurisdiction you did not choose. Your traffic crosses their network, where it is logged. Your users reach you through an account system that identifies them to the provider too.

None of that is a bug in the cloud. It is the cloud. A landlord holds the keys by definition.

Figure 1. Two ways to not own the machines
One operator — the hyperscaler
  • Visibility. The operator runs the hypervisor, the storage layer and the network. Data is plaintext when queried, in an address space they own. Encryption at rest is decrypted by a key they also hold.
  • Control. Accounts suspended, regions withdrawn, prices and terms rewritten unilaterally. The dependency is asymmetric.
  • Identity. Every service is reached through an account tied to a legal identity and a payment instrument. Anonymity is excluded at the front door.
  • Failure domain. One company, one set of incentives, one legal jurisdiction.
Many operators — a network
  • Visibility. No single party sees the whole. Each tenant's data lives in its own processes on machines chosen from a pool, and the perimeter is a tunnel rather than a datacenter wall.
  • Control. No account to suspend. Nodes are replaceable and the network reconciles around a departure.
  • Identity. A signature, not an account. Nothing is collected, so nothing can be disclosed.
  • Failure domain. Many operators, many jurisdictions — which is a security property, not a marketing one.
The right-hand column is the claim, not the achievement. Sections 16 and 17 state precisely how far it currently holds and where it stops.

The usual answer to the left-hand column is self-hosting, and it does address all three rows. It also reintroduces exactly the problem the cloud solved: you are racking machines again, at one machine's worth of reliability. The honest version of that pitch is a trade of an operator you do not control for an operations burden you cannot carry.

A cloud does not have to be one company's datacenter. It can be a network of machines that many different people own, presenting one interface.

That reframing is not new — the internet already is such a network at the transport layer, and BitTorrent, Tor and IPFS each demonstrated it for storage and routing. What has not existed is the boring middle: a decentralized substrate offering the ordinary primitives an application needs. A SQL database. A cache. Somewhere to put files. A queue. Somewhere to run a function. A domain name with a certificate on it.

2What Orama is

A decentralized application platform, assembled from ordinary well-understood Linux services, running on VPS nodes that independent operators own, and presented to a developer through one SDK and one CLI.

Figure 2. Three commitments, and what each forces
Commitment 01 No shared substrate between tenants Multi-tenancy is physical, not a prefix on a row. A namespace is a real consensus group, a real cache ring and a real gateway process.

Forces: port blocks, process supervision, a scheduler — and a blast radius that ends at the tenant boundary.
Commitment 02 No plaintext on the public internet Exactly one security perimeter: a WireGuard mesh. Every service not deliberately public binds to an overlay address.

Forces: a short auditable public port list, and a join protocol that establishes the tunnel before any service starts.
Commitment 03 No passwords, no accounts Identity begins with a wallet signature and nothing else. No email, no password hash, no profile.

Forces: a scope system, because a credential that cannot be tied to a person must carry its own authority.
Everything in Part II is downstream of these three. Where the architecture looks unusual, the cause is almost always one of them.

Every node is the same node

There is no coordinator machine, no special node type and no privileged operator. Every node runs the same software; a node differs from its peers only in flags — whether it answers DNS, whether its operator opted into running an anonymity relay, and which tenants the scheduler placed on it.

What a developer gets

Eleven services, reachable through a single TypeScript client or the orama CLI, scoped to a namespace owned by the wallet that created it. Section 12 gives the full surface; the short version is that the primitives are the familiar ones, deliberately.

3What Orama is not

A whitepaper that only lists strengths is marketing. These are deliberate exclusions or honest current limits, and they belong before the architecture rather than after it.

Not this A blockchain Wallet signatures are used for identity because public-key cryptography is a better login than a password and collects nothing. That is the entire relationship. No chain, no consensus over application state, no token required to use the network, no contract in the request path. Consensus exists only where a database needs it — Raft, inside a tenant's own cluster, over that tenant's own rows.
Not this Censorship-proof Nodes are ordinary VPS instances at ordinary hosting providers. A provider can terminate a node and a determined adversary can lean on several. What the design buys is that no single node is load-bearing: a tenant's cluster spans three, deployments replicate, and the network reconciles around a departure. That is resilience, not immunity.
Not this A defence against a hostile hypervisor The most important limit in this document, and Part III is devoted to it. Orama runs on machines whose firmware and hypervisor belong to someone else. An adversary who can snapshot the memory of a running node, repeatedly and on demand, defeats every control described here.
Not this Finished Orama is alpha. It runs a development network and a test network with a real tenant in production use, and it is not open for public sign-ups. Several structural questions in Part V are genuinely unresolved — including whether the current two-plane split survives at all.
On the word "whitepaper"

In this industry the word has come to mean a fundraising document describing a system that does not exist yet. This one describes software that is running, and marks the parts that are not. It is not an offering document, it does not describe a token, and it makes no financial claim. Part V is the only forward-looking part; every item in it is written as an open question with its blockers, because that is what those items are.

Three claims we will not make

A claim you will not find hereWhy not
"Your data is encrypted, so it is private."Any store that answers a query holds the key and the plaintext in memory at query time. Encryption at rest addresses a disk, not a hypervisor.
"Decentralized, therefore unstoppable."The current network is a small number of nodes run by a small number of people. Permissionless participation is deliberately out of scope until a hostile node cannot harm a tenant — see Section 22.

4Two planes, one gateway implementation

The single most important structural fact about Orama is that the same gateway implementation runs in two different roles — once as the cluster-wide control plane, and once per tenant as a data plane.

Read this figure first; the rest of Part II follows from it. A request to a tenant is authenticated on the core gateway — where the API keys actually live — and then proxied inward with the verified identity stamped into internal headers. The tenant's gateway never has to trust the caller; it trusts the header, and the header only arrives over the overlay.

The two roles are the same code but not the same process. The control plane is embedded: orama-node starts it in-process, in its own address space, which is why no core gateway systemd unit exists on a node. The data plane is that same package compiled as a standalone gateway binary and run as one template unit per tenant. A reader looking for an orama-gateway service will not find one; the name survives only in legacy cleanup paths.

Almost every other property of the system is a consequence of this split. Ports are allocated in blocks because tenants get real processes. The trust boundary has to be a VPN because those processes talk across machines. Deployments need a home node because writes must land in exactly one place.

The seam is also a defect generator

Honesty requires noting that this split is the leading candidate for removal. Four separate defects trace directly to it: a gateway holding two database handles and silently writing tenant rows to the wrong one, API keys hashed differently by the two registries, namespace identifiers that are not portable between them, and configuration drift between the two gateway modes. Section 22 covers the proposal to collapse it.

Four tiers, four supervision models. The differentiators between one node and another are only: the --nameserver flag, the operator's anonymity-relay opt-in, and which tenants the scheduler placed here. Everything runs as an unprivileged user under systemd hardening; only the web server and DNS server may bind privileged ports, because only they need to.
Ordering is a hard dependency, not a preference

Tenant services are ordered database → cache → gateway by systemd dependencies. A gateway that starts before the cache is reachable does not fail permanently: it retries five times with exponential backoff, then keeps retrying in the background and enables its cache endpoints once the connection succeeds. Nothing in the codebase waits by sleeping — readiness is polled against the actual indicator with a timeout, because a sleep long enough on an idle machine is not long enough on a loaded one.

7One socket, three destinations

Port 443 does not belong to the HTTPS server. It belongs to a TCP proxy that reads the unencrypted TLS ClientHello, looks at the server name, and forwards raw bytes onward without ever terminating TLS.

Figure 7. What actually owns port 443
One public TCP socket — TLS bytes, not yet decrypted
orama-sni-router :443 peeks the ClientHello never decrypts copies bytes verbatim
┌──────────────────────────┼──────────────────────────┐
SNI matches cdn-<hash>.<base> TURN over TLS for one namespace — the stealth path. Hostname derived from a hash, so the SNI string does not name the app being blocked.
SNI matches turn.ns-<name>.<base> The same relay under a human-readable alias, for operator convenience.
Everything else caddy :8443 Terminates TLS, handles ACME, reverse-proxies to the core gateway on loopback.
Why bother: so that a media relay can share the HTTPS port. To a deep-packet-inspection middlebox in a jurisdiction that blocks voice traffic, a relayed call is indistinguishable from an ordinary HTTPS connection — same port, same handshake, and a hostname that looks like a CDN. Static operator routes win over auto-discovered ones on conflict, and a transient read failure keeps the previous route table rather than blackholing live traffic.
Privacy properties here are obtained by arranging ordinary components carefully, not by inventing cryptography. Nothing in that path is novel. The novelty is that it is wired up at all.

Certificates

The web server holds every certificate and serves the wildcard and apex for each zone. Certificates for tenant custom domains are issued on demand: the web server asks the gateway whether a hostname is one it should get a certificate for, and the gateway answers from its own domain table. Challenges are answered through a small custom plugin that writes the challenge record into the cluster's own DNS — so there is no external DNS provider anywhere in the certificate path.

8The network is its own nameserver

Nameserver nodes run CoreDNS with a plugin that reads the cluster database. The authoritative zone is a table. There is no zone file, and no external DNS provider anywhere in the system.

Why this matters more than it sounds. Adding a node, provisioning a namespace and issuing a certificate all become the same kind of operation: an insert. There is no configuration management system in the architecture because there is no configuration to manage.
The heartbeat runs even when registration failed

Each node registers itself at startup and re-asserts on a heartbeat. The heartbeat is deliberately independent of the initial registration succeeding — a node that boots during a leaderless window, which is common during a rolling restart, would otherwise stay marked inactive forever and silently drop out of both deployment routing and vault guardian discovery.

Custom domains

A deployment gets a generated subdomain reserved cluster-wide. A tenant may attach their own domain instead: add it, prove ownership with a TXT record, point an A record at the deployment, and the certificate is provisioned automatically. Ownership is verified before a certificate is requested, so the platform cannot be used to obtain certificates for domains the requester does not control.

In most platforms a tenant is a column. Here a tenant is a cluster — its own consensus group, its own cache ring, its own gateway process, on three real machines.

Four disjoint ranges, three allocators. Realtime uses entirely separate ranges so that adding voice to a namespace cannot disturb an existing core allocation. Allocation is optimistic rather than transactional — scan, insert, and let a uniqueness constraint reject the loser of a race, which retries with backoff. The twenty-tenant ceiling is a limit per machine, not on the network: growth is horizontal.

The tenant's tables live in the tenant's own database file, on the tenant's own replication log, reached through the tenant's own gateway on the tenant's own port. There is no query that can cross the boundary because there is no shared table to cross it in.

10Identity: wallet first, scopes second

Orama has no passwords. Identity begins with a wallet signature and everything downstream derives from it.

Figure 11. The credential ladder
START A walletEVM or Solana. Request a single-use nonce, sign it, submit the signature. The server recovers the address and binds it to a namespace.
↓ ISSUES A short-lived token  ·  and a scoped API keyRefresh tokens are stored as hashes, never plaintext. API keys are stored as HMAC hashes under a server-side secret. Both carry a grant set.
↓ EXCHANGE A key may be traded for a token — keeping the key's narrow grantsThis is the guard that closes exchange-then-escalate. A runtime key cannot be laundered into an administrative token by trading it in.
↓ GATE The scope gate — required grant per method and pathRuns after ownership, so it can only ever tighten an already-authorized request. It never authorizes on its own.
Two more guards make it hold. A wallet token is never trusted for a scope claim it happens to carry, even if a tenant's own claims provider injected one — the field is reserved and ignored on wallet subjects regardless. And a logged-in end user receives every data-plane grant and never administrative access — unless that wallet is a confirmed owner of the namespace, in which case the middleware marks the request owner-confirmed and the gate grants it admin. Ownership, not the token type, is what opens the control plane.
Figure 12. Grants by profile — what a client bundle may safely ship

Eight grants are defined, but only seven can currently be minted onto a key: pubsub is missing from the issuance allow-list, so a request for it is rejected as unknown — by an error message that lists it as valid. A pubsub route is therefore reachable today only by a user token or an admin key.
Administrative access is a wildcard that satisfies every requirement. The only thing standing between a leaked client key and the control plane is that the key was never minted with that grant — which is why the profiles exist. Keys minted before scoping existed stored a null scope, read as administrative; a grandfather branch kept them working across a rolling upgrade and a sweep then revoked them so the branch stopped mattering.

11The path a request takes

Every request that survives the edge lands on one multiplexer wrapped in a fixed nine-layer chain. The order is deliberate, and one ordering decision in it is load-bearing.

Figure 13. Nine layers, then a handler
1 · LoggingRequest identifiers assigned before anything can fail
↓
2 · Security headers    3 · Rate limit    4 · CORSPer-IP limiting happens before any work is done on behalf of the caller
↓
5 · Domain routing  — THE FORKRuns before auth, because the Host header alone decides whether the request belongs to this gateway, to a tenant's gateway, or to a deployed application
↓

Domain routing before auth, scope after ownership. The first ordering is required because a request for a deployed application is not addressed to the gateway at all. The second is a safety property: a gate that runs after authorization can only ever subtract.
One deliberate exception

A host of the form ns-<name>.<base> is proxied inward regardless of path — except for scoped key management, which operates on the cluster database where keys are validated. Namespace gateways have isolated databases without the authoritative key table, so proxying those writes would land keys in a database that can never authenticate them.

Reads are everywhere, writes are somewhere

Any node can answer a request for a deployment. State-changing operations — update, delete, rollback, logs, statistics — are funnelled to that deployment's home node, so two gateways never mutate the same application concurrently. The forwarding proxy is loop-guarded by a header: a request already forwarded once is handled locally rather than bounced again.

The vault: stated plainly

The design is sound — the client, not the server, splits a secret, and fewer than a threshold of guardians reveals zero information regardless of computing power. The defects are in the implementation. Guardian discovery is a stub: it returns an empty node list and reports success, so the self-only fallback never fires and a guardian starts knowing no peers. The newer named-secrets API authenticates with a session token that any caller knowing the identity can mint, because the challenge is the server's own value replayed back with no proof of key possession — the older push and pull paths do require a real signature. And the node agent carries a fourth, separate implementation of the sharing scheme that infers each share's position from where it sits in the collected slice, so skipping one unreachable guardian silently reconstructs the wrong key. It is not a service to trust with a secret today.

The Host header decides everything. A static deployment never reaches a process; a dynamic one is proxied to a local replica; anything that changes state is forwarded once to the node that owns the deployment. The two subsystems are separate: deployments and functions share neither a route nor a type.
Recursion is bounded, not forbidden

A function can publish a message, and a published message can wake a function. Dispatch therefore carries an explicit depth parameter, and nested chains are bounded; the local fast path is subject to the same depth accounting. Once-per-publish dedup — an in-process cache plus a cluster-wide claim — guards the shared dispatch entry point, while the local path fires only wildcard-pattern matches on the publishing gateway itself.

Clients cannot reach the forwarding unit directly, so all media must traverse a relay, and the server enforces relay-only transport so that no direct connection is even attempted. The consequence is that two people on a call never learn each other's addresses. Combined with the TLS listener sharing port 443, a call is both unlinkable between participants and, to an on-path observer, not obviously a call. Stated precisely: the signalling listener is configured to the overlay address by provisioning convention rather than by a validated invariant, and the media sockets are not interface-bound at all — what keeps the unit off the public internet is the firewall, which never opens its ports.
A gap that was real, and is closed

Node replacement used to leave realtime role allocations attached to the departed machine — one cause behind three visible symptoms: a namespace losing relay redundancy, crash loops on replacement nodes, and orphaned allocations. It is fixed. A reconciler now runs on a sixty-second loop, revoking roles held by members that are no longer viable and re-allocating to live ones, under a majority quorum guard and a single deterministically elected coordinator. The residual is review follow-ups on that fix, not a missing migration.

15Storage, and what deletion means

Content-addressed storage is straightforward until a user asks for something to be deleted. Then the question is whether the bytes actually left the disks, and the honest answer requires more than an unpin.

Figure 18. Two reclaim paths, and why both exist
01UploadContent is added and pinned across the cluster; ownership is recorded against the namespace
→
02UnpinOwnership is verified first, so unpinning is tenant-isolated. The pin is removed — but the blocks are still on disk
Path A · scheduled Garbage collection on a timer A repository collection runs on a six-hour cycle and reclaims unpinned blocks. Adequate for ordinary space management. Not adequate when a user has asked for something to be gone.
Path B · immediate Overlay-driven eviction An internal, overlay-only endpoint fans out per-node block eviction. This is the privacy-grade path: when someone deletes content and expects the bytes to leave the disks, waiting six hours is not an acceptable answer.
Why the distinction is in a whitepaper at all: because "delete" meaning "eventually, probably" is the default behaviour of content-addressed storage, and a platform that markets privacy has to close that gap explicitly rather than inherit it.

Capacity is derived, not fixed

The storage ceiling on a node is a share of that node's actual disk rather than a constant, so a larger machine contributes more without reconfiguration. A swarm-sync loop keeps every node connected to every cluster peer, so a node that restarts cannot silently end up isolated while its daemon still reports healthy. Per-namespace byte quotas are checked server-side before every upload and pin, with a replication-aware projection — but they are opt-in and currently dormant: a namespace with no quota row is treated as unlimited, nothing yet writes that row, and a lookup error fails open.

The limit of "deleted"

Even immediate eviction does not erase history everywhere. A deletion is itself a replicated log entry, so the original write — with its payload — persists in the replication log and its snapshots until compaction, which is driven by size and count thresholds rather than by any privacy requirement. Deleting is not erasing, and a system that claims otherwise is not describing its own storage layer accurately.

16The adversary, stated plainly

Most platforms describe their security posture in terms of what they encrypt. That is the wrong frame, because it invites the reader to assume a threat model that was never stated. This section states one.

The adversary Orama designs against is the hosting provider, or an agency with legal or covert access to one. That adversary can take a full disk snapshot, take a full memory snapshot at the hypervisor, boot a clone of any disk image, and observe all datacenter traffic. We control neither the hypervisor nor the firmware, and confidential computing is not purchasable on budget hosting.

Figure 19. The conversion this design buys
Cheap path — what we move things out of
  • Retroactive. A backup taken months ago still yields today's secrets.
  • Scales to everyone at once. One API call captures every customer on the host.
  • Deniable and traceless. Nobody has to decide to target you specifically.
  • Asynchronous. Grab the image now, read it whenever.
Expensive path — what we move things into
  • Targeted. Requires a decision about a named machine.
  • Synchronous. The process has to be running at the moment of capture.
  • Repeated. Once is not enough; keys rotate and sessions end.
  • Human-visible. Somebody has to authorise it, and keep authorising it.
That conversion is the entire product of the privacy work. It is not nothing — but it is also not invisibility, and it should never be sold as such. Nothing here makes capture impossible, and any claim otherwise about software running on rented machines is false.

The current state, without euphemism

A dedicated security review of this codebase — one that assumes the hosting provider, not a remote attacker, is the adversary — produced ninety findings, twenty-seven of them critical, and was independently re-verified before being filed as seven pending workstreams. Measured against today's baseline, where the cluster secret, the storage swarm key, the key-hashing secret and the tunnel private key all sit in plaintext on disk, its conclusion is that one disk snapshot of any single node is a total, permanent, offline compromise — including from a backup taken months ago or a disk decommissioned last year. Publishing the number is the point: a platform asking to be trusted with private data should show its audit, not its logo.

17What holds, and what does not

Figure 20. Property, mechanism, and the attack that still wins

The right-hand column is the honest one. Only properties that are absences — a credential never collected, a hostname that reveals nothing — survive an adversary reading process memory. Everything achieved by encryption fails there, because a store answering a query holds the key and the plaintext at query time.

The strongest property is an absence

Authentication is a signature. There is no email address, no password hash, no phone number and no profile — not because they are protected but because they are never collected. A demand served on an operator for a user's identity returns a public key, because a public key is all that exists. This costs nothing to operate, because it is an absence rather than a mechanism, and it is the only property in the table that no capture defeats.

Three things that are not defended

MemoryA database answering a query holds key and plaintext in memory. True of every store, bespoke or not. Rewriting the storage engine would move plaintext from one address space to another that the same hypervisor reads.
MetadataWhich nodes talk to which, how often, in what volume, when. The tunnel does not hide it. Value-level encryption also leaves residue in log structures and write-ahead files. Metadata is the price.
CompulsionAn operator who can be compelled can be compelled. Splitting secrets raises the number of parties who must be — a real improvement in a jurisdictionally diverse network, and none at all if every node sits with one provider in one country.
Why publish the limits

Because a user who believes a system defends against memory capture will make decisions — about what to store, and about whom to store it for — that the system cannot support. Overstating a threat model does not protect anyone; it transfers risk to the people least able to evaluate it. It also has a direct architectural consequence: operator diversity is a security property, not a marketing one, and it is the property the network most needs to grow.

18How a node joins

There are no shared secrets on a command line. A node joins with a single-use, time-limited invite, and the tunnel is established before any cluster service starts.

Figure 21. The join sequence
01 · MINT An operator mints an invite on an existing nodeA row lands in the invite table and the CLI prints the full join command. The token is single-use and time-limited.
02 · CALL The new node calls the join endpoint over HTTPSWith certificate pinning on first use. Never on the gateway's own port — the firewall blocks it, and that mistake is the most common failed install.
03 · CONSUME The handler validates and atomically consumes the tokenIt allocates an overlay address and returns the cluster secret, database credentials, cache key, storage swarm key and the current peer set.
04 · PEER The joiner brings up its tunnel and registers its public keyEvery existing node reconciles the new peer from the authoritative peer table — no manual configuration on any other machine.
05 · START Only now do database, cache, storage and gateway startAll of them dialling peers on overlay addresses, never public ones.
06 · ANNOUNCE The node registers in the DNS table and begins its heartbeatIts lifecycle state moves from joining to active, and metadata is republished to the discovery layer.
The ordering is the security property. No cluster service is ever reachable before the tunnel exists, and no secret ever travels outside it — with one exception noted below, which is a defect rather than a design.
Not yet true for the dedicated image

The flow above describes the standard install. The enrollment path used by the dedicated node image is currently weaker: its completion endpoint is unauthenticated, and it ships the node's own tunnel private key and the cluster secret over plaintext HTTP. Rewriting that wire protocol is tracked work, and until it lands the network cannot safely admit a node operated by someone unknown — which is precisely the property a decentralized network needs.

19The rule that cannot be bent

The control plane is a Raft cluster, and Raft needs a majority of voters. Everything about how Orama is operated follows from that one sentence.

Losing a majority simultaneously loses the cluster. This is stated in a whitepaper rather than left to a runbook because it constrains the architecture: any future change that makes restarts more frequent, or that increases the number of quorum-holding services, is paying a real cost that has to be justified.

Verification against the real thing

A lesson worth recording: the cluster database is not a local SQLite file, and behaviour that passes against one can still fail on the cluster. A row-eviction defect shipped exactly that way — correct against every local test, wrong in production. Live verification against a real cluster, plus reading the gateway logs, is the only sufficient test for storage-layer changes.

Two handles, one silent failure

The gateway holds a handle bound to the cluster's own database and a handle bound to a namespace's. Namespace-scoped data written through the wrong one lands in a database it will never be read back from — and nothing errors. It fails silently, which is the worst failure mode available, and it is the clearest example of the hazard the two-plane architecture creates.

20A node an operator cannot log into

A purpose-built node image exists: no SSH, no shell, a read-only root filesystem verified at the block level, an encrypted data partition, and exactly one root process that is the entire userland. It has never been run.

Read this before the rest of the section

What follows is a design that is built but untested. The image has not been booted in anger; its agent has no test files; integrity verification is compiled but not wired into boot; the syscall filter is never loaded into any process; and a signature-verification defect means no over-the-air update can currently be applied in the field. The present proposal is to exclude it from the first release and run hardened Ubuntu instead. It is described here because it is the direction, not because it is the status.

Figure 23. The intended boot chain

The intent: no path from physical possession of a machine to reading its data — the disk encrypted, the key existing only as shares on other machines, and no shell in which to ask for it. A node removed from the network cannot be booted in isolation either. Stages 01 and 04 are not yet wired up in the shipped image.

The design claim, and its honest limit

Removing the shell removes the most common path from operator to tenant data, and encrypting the disk with a key the operator never holds removes the offline one. Neither removes the hypervisor. An operator who is also the hosting provider — or who runs the image on hardware they control at the firmware level — is outside what this defends.

The sharper research question, and the one currently on the table, is not which distribution to fork but what does this platform require that an existing minimal, API-driven, shell-less operating system does not already provide? Forking one means inheriting a security-update treadmill indefinitely, which for a small team is the thing most likely to kill the project.

What is not ready, in detail

The network is not open for public sign-ups and should not be. Secret custody is not usable. The dedicated image has never booted. There is no tenant-facing monitoring on either network: the only cluster observability is a pair of CLI tools that connect to each machine over SSH, which makes them operator-only. What a tenant can see is a health endpoint, a namespace status and per-deployment logs. And that health endpoint is structurally optimistic — a subsystem whose client was never constructed reports unavailable, which the aggregate counts as healthy, so a gateway with no cache connection at all still answers "healthy".

A security audit of our own system produced sixty-two findings that remain entirely untouched, and a later hardening sweep added more. Secret rotation is operationally impossible today: there is no key identifier in the encryption envelope, no re-encryption tool, and no rotation mechanism for the tunnel keys at all — so a key captured today stays valid indefinitely and there is no response available to a suspected compromise.

The scale question, asked honestly

The architecture has been exercised at the scale of a handful of nodes and a handful of tenants. Twenty namespaces per node is a designed ceiling; what has not been demonstrated is a network of hundreds of nodes with hundreds of tenants, operated by people who do not know each other. That is the real test of the thesis, and it has not been run.

None of these are research problems. They are unfinished engineering, which is a different and more tractable category — but the distance is real and this document is not going to shorten it rhetorically.

Whether that literal is a defect or a product constraint is undecided — and requiring three machines to evaluate the platform is a barrier to operator diversity.

23Colophon

Orama is a working decentralized application platform with a real tenant, a coherent architecture, an unusually candid audit of itself, and a substantial amount of unfinished work between here and something a stranger should trust.

The thesis — that the ordinary primitives of a cloud can be delivered from machines that many different people own, through an interface a developer already understands — is demonstrated at small scale. Whether it survives contact with hundreds of nodes and operators who do not know each other is the open question, and the only one that ultimately matters. We have tried to describe the system in terms that make that question answerable by someone outside the project, including by reporting the defects that would have been easier to omit.

Why permissionless nodes are deliberately out of scope

Permissionless participation requires that a hostile node be unable to harm a tenant, and the gaps in Section 21 are why that is not yet true. Opening node operation first would not be decentralization; it would be an unguarded multi-tenant system with more participants. The order is: make one tenant safe from another, then make the network safe from its own nodes, then open it.
