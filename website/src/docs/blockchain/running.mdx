# Running a chain node

`orama node install` does not start the chain. The chain has its own installer, `chain/scripts/stagenet/deploy.sh`, and that script refuses to run unless the chain id contains `-stagenet-` or `-devnet-`. The default chain id is `orama-stagenet-1`.

The script is explicit that this is temporary. A global-node role that would let `orama node install` manage `oramad` does not exist yet. The script also uses an unencrypted test keyring. That is a devnet convenience. It is not acceptable once the token has value outside a test.

The script's own epoch is 300 seconds and 10 blocks. Production parameters require 24 hours and 14,400 blocks unless `--allow-bootstrap-stake` is set, which that devnet path does set.

## Process

| | |
|---|---|
| Binary | `oramad` |
| Unit | `orama-global-chain.service` |
| User | `orama-chain` |
| Home | `/var/lib/orama-global/chain` |

The unit is not one of the `orama-namespace-*` services. Stopping the Orama node supervisor does not stop the chain, and the chain installer does not touch the cluster's other services.

## Ports

| Port | What | Where it listens |
|---|---|---|
| 31000 | CometBFT peers | The WireGuard address |
| 31001 | CometBFT RPC | 127.0.0.1 only |
| 31002 | Cosmos gRPC | Local |
| 31003 | Cosmos REST | Local |
| 31004 | Prometheus | 127.0.0.1 only |

The Orama node reads height, block time, and whether this machine is a validator from the RPC on 127.0.0.1:31001. It does not import the chain's Go types.

## What a running chain is not

Installing this unit does not put ORAMA in front of apps. Gateway requests stay on the gateway. The two networks described in the whitepaper, devnet and testnet for the platform, are still installed with `orama node install`. Whether `orama-global-chain` is up on a given machine is a fact about that machine, not a consequence of installing Orama.

Queries against the chain use `oramad query`. The platform CLI `orama` does not wrap them.
