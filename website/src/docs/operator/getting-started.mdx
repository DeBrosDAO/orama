# Getting Started as a Node Operator

Node operators are the backbone of the Orama Network. By running a node, you contribute compute, storage, and bandwidth to the decentralized infrastructure. This guide covers what operators do, what you need, and how to join the network.

## What Operators Do

As a node operator, your server becomes part of the Orama mesh network. Your node will:

- **Route traffic** through the API gateway for applications deployed on the network
- **Store data** in distributed databases (RQLite) and cache layers (Olric)
- **Host files** on IPFS with cluster-level replication
- **Execute functions** in the WASM serverless runtime
- **Relay messages** through the PubSub system
- **Serve DNS** if configured as a nameserver node (CoreDNS)
- **Route outbound requests anonymously** through a local Tor client (SOCKS5 proxy)

All inter-node communication happens over an encrypted WireGuard mesh network on the `10.0.0.0/24` subnet.

## Hardware Requirements

| Resource | Recommended |
|----------|-------------|
| CPU | 4 vCPUs |
| RAM | 8 GB |
| Storage | 160 GB SSD |
| Network | 1 Gbps, unmetered or high bandwidth cap |
| OS | Ubuntu 22.04 LTS |

The installer enforces a hard minimum of 2 vCPUs, 2 GB RAM, and 10 GB free disk (`orama node install --skip-checks` bypasses this, but is not recommended). A stable network connection with low latency is important for Raft consensus and mesh connectivity.

## On your computer

`orama node setup` runs on your computer, not on the VPS. Install these before you rent one.

**The `orama` CLI.** Homebrew installs the latest stable release:

```bash
brew install DeBrosDAO/tap/orama
orama version
```

Debian and Ubuntu packages, and prebuilt tarballs for macOS and Linux, are on the [releases page](https://github.com/DeBrosDAO/orama/releases). From a checkout of this repo, `make build` writes `./core/bin/orama`. The same install notes are in the [CLI reference](/docs/developer/cli-reference).

**RootWallet, unlocked.** Download the desktop app from the [RootWallet releases](https://github.com/DeBrosDAO/rootwallet/releases): a universal `.dmg` on macOS, or a `.deb` or AppImage on Linux. The `rw` command uses the same vault as the app. Orama asks that app for SSH keys and signatures. It does not ask you to paste them into the terminal.

**The VPS login, if the machine has a password.** Store it once. The command asks for the username and the password:

```bash
rw vault add <VPS_IP>
```

Use the SSH username you will pass to setup. That is `root` unless you pass `--user`. `--password` on `orama node setup` is a switch. It does not take the password. It reads this vault entry for that IP and username.

**The build archive.** On your computer:

```bash
orama build
```

The command prints `Archive: /tmp/orama-<version>-linux-<arch>.tar.gz`. Pass that path as `--archive`. Setup stops if the flag is missing. The archive must be signed; an unsigned build will not install.

The VPS itself gets its `orama` binary from that archive. You do not copy a binary onto the server by hand.

## Joining the Network

You also need a VPS that meets the hardware requirements above.

### Setting Up Your First Node (Genesis)

The first node creates a new cluster. Run this from your **local machine** (not the VPS):

```bash
orama node setup \
  --ip <VPS_IP> \
  --password \
  --archive /tmp/orama-<version>-linux-amd64.tar.gz \
  --env devnet \
  --base-domain <BASE_DOMAIN> \
  --role nameserver \
  --genesis
```

`--password` only works after `rw vault add <VPS_IP>` with username `root`. If you omit `--env`, setup uses the active environment and does not ask which one. `orama env list` and `orama env current` show that choice. `orama env use <name>` changes it.

This single command:
1. Creates an SSH key in your RootWallet vault
2. Installs the SSH key on the VPS, using the vault password once
3. Uploads the binary archive
4. Installs and starts all services
5. Records the environment for this cluster. It does not switch the active environment.

After genesis, the new environment is recorded and the active one is left as it was. Point the CLI at the new cluster, then sign in:

```bash
orama env use devnet
orama auth login
```

`orama auth login` follows the active environment. If `--env` named an environment that was already active, its gateway URL was updated in place and `orama env use` is unnecessary.

### Adding More Nodes

Once the genesis node is running and you're authenticated, add more nodes with one command:

```bash
# Add a nameserver node
orama node setup \
  --ip <VPS_IP> \
  --password \
  --archive /tmp/orama-<version>-linux-amd64.tar.gz \
  --env devnet \
  --base-domain <BASE_DOMAIN> \
  --role nameserver

# Add a regular node
orama node setup \
  --ip <VPS_IP> \
  --password \
  --archive /tmp/orama-<version>-linux-amd64.tar.gz \
  --env devnet \
  --base-domain <BASE_DOMAIN>
```

### A key-only server

Some images have no password login. They open with a key you already have, often as user `ubuntu`. Do not pass `--password`. Pass that key once so setup can install the RootWallet key:

```bash
orama node setup \
  --ip <VPS_IP> \
  --user ubuntu \
  --bootstrap-key ~/.ssh/id_ed25519 \
  --archive /tmp/orama-<version>-linux-amd64.tar.gz \
  --env devnet \
  --base-domain <BASE_DOMAIN>
```

`--password` and `--bootstrap-key` are alternatives. The command rejects both at once. If you pass neither, setup assumes the RootWallet key is already on the server.

The setup command automatically:
- Creates a unique SSH key for the node in RootWallet
- Installs that key on the VPS, once, using the vault password or `--bootstrap-key`
- Requests an invite token from the cluster (using your wallet authentication)
- Uploads the archive and runs the full installation
- Joins the node to the cluster

After that first connection, SSH uses the RootWallet key. The vault password and the bootstrap key are not used again.

### Setup Flags

| Flag | Required | Description |
|------|----------|-------------|
| `--ip` | Yes | Public IP address of the VPS |
| `--archive` | Yes | Path printed by `orama build`. Setup stops without it. |
| `--password` | No | Switch. Read the VPS login from the RootWallet vault (`rw vault add <ip>`). Do not put the password after this flag. |
| `--bootstrap-key` | No | Private key that already opens a key-only VPS. Used once, not stored. Not together with `--password`. |
| `--user` | No | SSH user (default: `root`). With `--password`, this must be the username stored by `rw vault add`. |
| `--env` | No | Target environment. Omitted, setup uses the active environment and does not ask. |
| `--base-domain` | For genesis | Base domain for the network (e.g., `orama-devnet.network`). A genesis node needs it. |
| `--role` | No | `node` (default) or `nameserver` |
| `--gateway` | No | Gateway URL override for invite tokens |
| `--genesis` | No | Create a new cluster (first node only) |

## What the Installer Does

The `orama node install` command configures the entire node automatically:

1. Validates system requirements (RAM, CPU, disk)
2. Generates a WireGuard keypair and establishes mesh tunnels to all peers
3. Configures and starts RQLite (distributed SQL)
4. Configures and starts Olric (distributed cache)
5. Configures and starts IPFS + IPFS Cluster (distributed storage)
6. Configures and starts the API gateway
7. If `--nameserver`: configures CoreDNS and Caddy for DNS and TLS
8. Installs the Tor client from `deb.torproject.org` (client only; SOCKS5 on `127.0.0.1:9050`, used for `/v1/proxy/anon`), removing the Anyone network first if an older install left it
9. Sets up systemd services with dependency ordering
10. Configures the UFW firewall (unless `--skip-firewall`)
11. Registers the node with the cluster

## Node Management

After installation, your node is automatically registered with your wallet. Use these unified commands from your local machine:

```bash
# List all your nodes
orama nodes --env devnet

# Check health of all your nodes
orama status --env devnet

# SSH into any node
orama ssh <IP>

# Rolling upgrade all your nodes. Nothing restarts without --yes.
orama rollout --env devnet --yes
```

See [Node Management](/docs/operator/node-management) for the full guide.

### On-Node Commands

These commands run directly on a VPS with `sudo`:

```bash
# Check service status
sudo orama node status

# Start/stop/restart all services
sudo orama node start
sudo orama node stop
sudo orama node restart

# Run diagnostic checks
sudo orama node doctor

# View service logs
sudo orama node logs <service>

# Output node health data as JSON
sudo orama node report --json
```

## Upgrading

Deploy new code to all your nodes with one command:

```bash
orama rollout --env devnet --yes
```

`orama rollout` builds an archive, pushes it, prints the restart plan, and stops unless `--yes` is passed. It does not use an archive you built earlier. To roll out a specific archive, pass `--no-build --archive <path> --yes`. After each node restarts, the command waits for that node to rejoin before it touches the next one. `--delay` is that wait, in seconds. The default is 300. It is not a pause between nodes.

Or upgrade a single node directly on the VPS:

```bash
sudo orama node upgrade --restart
```

See [Upgrades](/docs/operator/upgrades) for the full rolling upgrade procedure.

## Monitoring

Quick health check of all your nodes:

```bash
orama status --env devnet
```

For detailed monitoring with cross-node analysis and alerts:

```bash
# Interactive TUI
orama monitor --env devnet

# Full cluster report (JSON)
orama monitor report --env devnet

# Active alerts only
orama monitor alerts --env devnet
```

All monitor subcommands support `--json` for machine-readable output and `--node <IP>` to filter to a specific node.

See [Monitoring](/docs/operator/monitoring) for the full monitoring guide.

## Single-VPS evaluation

A single VPS can run Orama end to end: the index plane on that machine, then a tenant namespace on the same machine, then an app with a database. That path is for evaluation, not production HA.

#### What the code does

Index membership is every node (`MembersAll`). One machine *is* the whole
index. Tenant provision looks at how many members the fleet has: every node
registered and not retired (`orama node remove`), whether or not it is
heartbeating or has a free namespace slot. A stopped or stale node that was
never removed still counts.

| Members | Tenant size | Notes |
|---|---|---|
| 1 | `BlueprintTenantN(1)` | Same units (`orama-namespace-{rqlite,olric,gateway}@<name>`), replica count 1. RQLite is leader, no `-join`. |
| 3 or more | `BlueprintTenant()` — N=3 | Production default. A 10-node fleet still provisions tenants at 3, not 10. |
| 0 | refused | Nobody to run on. |
| 3 or more, fewer than 3 with a free slot | refused | The fleet is full. The create answers 503 `NAMESPACE_CAPACITY` ("a namespace needs 3 nodes with a free namespace slot and N have one"); nothing is created and the name is not taken. It used to count free slots, so a full five-node fleet with one slot left provisioned an eval namespace on that node, all three roles on one machine, and reported it ready. |
| 2 | refused | Neither eval nor HA. Even-sized Raft is a split-brain. Add a third node. |

There is no second “dev mode” that skips systemd or blueprints, and no
`--replicas` flag. The create API is still `POST /v1/namespaces` with `{name}`.

Vault is an index service (one guardian per node). On one VPS there is one
guardian. Shamir cannot split (`K` is floored at 2). The gateway stores the
envelope as a **local key** on that disk (`K=1`, `W=1`) and logs it. That is
not information-theoretic secret sharing: lose the disk, lose the secret.
Production (`N≥3`) is unchanged: `K = max(2, floor(N/3))`.

WebRTC stays unavailable (`need at least 3` for SFU/TURN). Do not enable it on
eval.

Bounce of the only node is local restore. There is no spare machine to fail
over onto. Disk loss is namespace loss.

#### Operator path

Genesis on the VPS (nameserver so the node has DNS):

```bash
sudo orama node install --vps-ip <ip> --domain <domain> --base-domain <domain> --nameserver
```

Or from your machine, with RootWallet unlocked:

```bash
orama build   # prints the archive path
orama node setup --ip <ip> --password --env <env> --archive <archive path> \
  --base-domain <domain> --role nameserver --genesis
# --password reads the VPS login from your RootWallet vault (rw vault add <ip>)
```

Then:

```bash
orama auth login
orama namespace create myapp
orama auth login --namespace myapp
```

`namespace create` on a one-node fleet no longer fails with
`insufficient nodes available for cluster`. The cluster row stores replica
counts 1/1/1 so repair does not try to grow it to 3.

This is not a substitute for the [three-nameserver cluster install](/docs/operator/node-setup#installing-a-three-nameserver-cluster-with-orama-node-setup) or for the rolling-upgrade rules on [Upgrades](/docs/operator/upgrades). Those remain the cluster path.
