# DNS and nameservers

An Orama cluster is its own DNS server. Its base domain, and every name under it (each deployment, each namespace gateway, each node, the TURN hosts) is answered by CoreDNS running on the cluster's nameserver nodes, from a table in the replicated registry. For the internet to ask your nodes, the **parent zone** of the base domain must delegate to them: NS records naming the nameservers, and *glue* A records giving their addresses.

This page explains the records, how to choose the base domain, how to create the records, and how to verify them.

## Why you need your own nameservers

- Deployments get names like `myapp-f3o4if.cluster.example.com` the moment they are created. A row is inserted, and the next DNS query sees it. There is no zone file and no external DNS provider.
- Certificates are issued through the ACME DNS-01 challenge. The challenge record is served by your own CoreDNS, and the certificate authority finds that CoreDNS through the delegation. **Until the parent zone delegates to the cluster, the genesis node cannot get a certificate.**
- Wildcard names (`*.cluster.example.com`) work for every subdomain.

## Nameserver slots

Each node installed with `--role nameserver` (`--nameserver` on `orama maint node install`) claims a slot, `ns1`, `ns2`, and so on, the first time its DNS sweep runs (every 30 seconds, once it has registered). Slots are claimed dynamically, lowest free number first, so **you cannot know in advance which address holds which name**. A node keeps its slot across restarts and missed heartbeats. Two minutes of silence takes it out of the round-robin, not out of its slot, because freeing the slot would drop the zone's glue. `orama node remove` releases the slot. There are at most 13 slots.

Each slot holder writes its glue record `nsN.<base>` pointing at its public IP. The zone's own NS set and SOA derive from the slots: one NS record for every slot that has glue. A one-nameserver cluster publishes only `ns1`; a five-nameserver cluster publishes `ns1` to `ns5`.

To see which address holds which slot, ask the cluster:

```bash
orama node dns delegation --env mycluster
```

```text
; cluster.example.com — create these in the parent zone example.com: as records in that zone, wherever its DNS is hosted
cluster.example.com.	IN	NS	ns1.cluster.example.com.
cluster.example.com.	IN	NS	ns2.cluster.example.com.
cluster.example.com.	IN	NS	ns3.cluster.example.com.
ns1.cluster.example.com.	IN	A	203.0.113.10
ns2.cluster.example.com.	IN	A	203.0.113.11
ns3.cluster.example.com.	IN	A	203.0.113.12
```

The fields are separated by tabs. When the base domain is a whole registered domain, the header reads `.com: at your registrar, as custom nameservers with glue (host) records` instead. After the records, the command asks DNS whether the parent zone returns them and says which NS or glue record is missing or points at another address, and it stores that answer on the environment. `--json` prints the same as data, with `delegated` and `findings` for each domain. It reads the registry over SSH from the environment's recorded nodes, so it works before the cluster's name resolves, and it lists only slots whose glue exists. **Run it again after adding or removing a nameserver, and update the parent zone to match.**

## NS records and glue

The NS records tell resolvers which servers are authoritative for the base domain. Because those servers are named inside the domain they serve (`ns1.cluster.example.com` serves `cluster.example.com`), resolving them would need the very servers they name. So the parent also carries **glue**: an A record for each nameserver name, handed out alongside the delegation.

## Choosing the base domain

### A subdomain (recommended)

Delegate a subdomain such as `cluster.example.com` from the `example.com` zone you already have. The NS and glue records are ordinary records inside the parent zone, created wherever that zone's DNS is hosted. The registrar is not involved and the rest of the domain keeps working.

This is the **only** option for a domain registered with Cloudflare Registrar, which does not let its domains use custom nameservers.

In the Cloudflare dashboard, for the parent zone: DNS, then Records, and add one row for each line the command printed:

| Type | Name | Content | Proxy status |
|---|---|---|---|
| NS | `cluster` | `ns1.cluster.example.com` | not applicable |
| NS | `cluster` | `ns2.cluster.example.com` | not applicable |
| A | `ns1.cluster` | the IP printed for ns1 | **DNS only** |
| A | `ns2.cluster` | the IP printed for ns2 | **DNS only** |

The glue A records must be **DNS only** (grey cloud). A proxied record answers with Cloudflare's addresses and resolvers would send your cluster's queries there. Any DNS host works the same way; the records are what matter.

`--cloudflare-token-file` writes the records into the parent zone for you when it is hosted at Cloudflare, then checks DNS. It refuses a registry TLD (a parent with no dot, such as `com`):

```bash
orama node dns delegation --env mycluster --cloudflare-token-file /path/to/cloudflare-token
```

### A whole registered domain

Use the registered domain itself (`example.com`) as the base domain. The NS and glue records then live at the registry and are set through your registrar: glue first (called *host records*, *child nameservers* or *personal DNS servers*), then the domain's nameservers switched to the `nsN` names.

- **Namecheap:** Domain List, Manage, **Advanced DNS**, *Personal DNS Servers*: add each `nsN.<domain>` with its IP. Then **Domain**, *Nameservers*, **Custom DNS**, and enter the `nsN.<domain>` names.
- **GoDaddy:** **DNS**, *Hostnames*: add each `nsN` with its IP. Then *Nameservers*, **Change**, *Enter my own nameservers*.
- **Cloudflare Registrar:** not possible. Use a subdomain.

Registry changes can take hours to propagate (up to 48); most are visible within 1 to 4 hours. The cluster then answers for the whole domain, because its nameservers are the domain's nameservers. Prefer a subdomain unless the domain is dedicated to Orama.

## Order: delegation before certificates

1. Install the genesis node with `--role nameserver --genesis`.
2. About 30 seconds later it holds `ns1`. Run `orama node dns delegation --env <env>` and create the records.
3. Wait until `dig NS <base> @8.8.8.8` shows the delegation. The genesis node's certificate is issued then. Caddy keeps retrying; nothing needs restarting.
4. Join the other nameservers. The invite pins the genesis certificate, so it must exist.
5. Run `orama node dns delegation --env <env>` again and add their records.

Full sequence: [Install a cluster from scratch](/docs/operator/install-from-scratch).

## Verify

```bash
orama node dns delegation --env mycluster    # what it should be
dig NS cluster.example.com @8.8.8.8           # what the internet sees; the same nsN names
dig A ns1.cluster.example.com @8.8.8.8        # glue; the IP printed for ns1
dig @ns1.cluster.example.com test.cluster.example.com        # your nameserver directly
dig @ns1.cluster.example.com myapp.node-abc123.cluster.example.com   # wildcard
```

For global propagation use dnschecker.org or whatsmydns.net. Inside the CLI, `orama status dns --env mycluster` shows CoreDNS, Caddy, certificate expiry and resolution tests.

## How the records stay correct

Per-namespace records are round-robin sets: `ns-<namespace>.<base>` (the gateway host), its `*.ns-<namespace>.<base>` wildcard, `turn.ns-<namespace>.<base>`, `turn-<namespace>.<base>` and the stealth TURN host, each with one A record per node serving that role. Every node runs these reconcilers, which are per-node and idempotent, so no leader election is needed:

| Reconciler | When | What it does |
|---|---|---|
| Ensure | WebRTC reconcile loop | Inserts this node's own A record if absent and re-enables it when this node's tenant gateway answers `/v1/health` |
| Withdraw and restore | Every 30 s | After 3 failed health probes soft-disables this node's own `ns-<ns>` rows, never the last active record for a name. Restores after 3 healthy probes |
| Purge | Every 30 s | Deletes A records of nodes that are non-active **and** silent longer than 15 minutes |
| Orphan purge | Every 30 s | Deletes per-namespace records whose namespace no longer exists |

Two safety properties: the staleness window (15 minutes) is far longer than the 120-second active-to-inactive flip, so a blip never deletes records; and the purge never empties a name, because deleting the last record of a namespace host would make the resolver fall through to the base wildcard and silently send clients to a node that does not host the namespace. A silent misroute is harder to diagnose than an outright failure. If a host is down to one record pointing at a departed node, add a replacement node and it re-advertises itself on the next sweep.

## Serving node names

On a network such as stagenet, an operator can claim a short identification name for each node on the chain (`MsgClaimNodeName`, see [Nodes](/docs/blockchain/nodes#identification-names)), and `<name>.<zone>` must then resolve to the node. The zone is a **dedicated sub-zone** below the network's base domain, for example `nodes.stagenet.orama.network`, never the base domain itself: a name is claimed by anyone, and under the base domain a claim such as `push` or `ns-myapp` would add an address next to the hostnames the cluster publishes there. The cluster whose nameservers answer the zone serves the names from the chain, with no one writing a record by hand. A name is an address record (A or AAAA) for each literal public IP among the node's endpoints, and nothing more: no NS record and no glue, so a name delegates nothing. A private cluster does not use this; it serves its own domain with its own NS and glue (above).

Turn it on in `node.yaml` of the cluster's nodes that have the chain next to them (a global layer installed on the same machine):

```yaml
http_gateway:
  base_domain: stagenet.orama.network
dns:
  node_names_zone: nodes.stagenet.orama.network   # empty or absent: this node publishes no names
```

Install the node with `--node-names-zone nodes.stagenet.orama.network` (`orama maint node install`, which writes the key into `node.yaml`), or write the key into `node.yaml` yourself and restart the node (`orama node restart`). The flag must name a zone strictly below `--base-domain`, and an install with any other value stops before it changes anything. `orama setup --create-network <name> --domain <domain>` passes `--node-names-zone nodes.<domain>` to every node it installs, because that cluster is the network's own and answers the network's names; a joining operator's private cluster (`orama setup --network <name> --domain <domain>`) passes none. An upgrade keeps it: `orama node upgrade` rewrites `node.yaml` from the template and carries `dns.node_names_zone` forward, and refuses to continue if the value in the file is no longer a valid zone. The zone must be strictly below the cluster's `http_gateway.base_domain`, in lower case with no trailing dot. The base domain itself, a domain elsewhere or a malformed value stops `orama-node` at start with the key's name in the message. Only the cluster that is the authority for the zone sets it.

Each such node pages the chain's `NodeNames` query (1,000 names a page) once a minute and keeps its `dns_records` equal to the answer, under the owner tag `node-names`:

- It adds the records that are missing, reactivates one that something deactivated, and removes the records of a name that was released or whose node's address changed. Records are added before any is removed, so a name that moves never stops resolving.
- It writes nothing unless it read the whole list. A chain that fails half way, a page key that repeats or more than a million names leaves the zone as it was and is logged as a failed pass (`Node names sync failed`).
- It removes nothing while the chain node may be behind: its status says `catching_up`, or its newest block (`latest_block_time`) is more than five minutes old, which also covers a node that stopped or was cut off while still reporting caught up. A pass also removes at most a quarter of the rows it owns, or 50 rows for a small zone, and logs `Node name removals held back` for the rest, so a truncated read costs a minute of DNS and not the zone; the next correct read puts the rows back.
- It publishes only a literal public IP. An address in a private, loopback, link-local, multicast or otherwise reserved range is refused and logged once (`Node name not published`), and so is a name that is not a valid label, a reserved label (the chain's reserved list is mirrored in `core/pkg/nodenames` and a test fails when the two differ) and a name that already has a record of another owner under the zone. Rows of any other owner are never touched.
- Rows are written 100 to a request, each request one transaction, and one pass writes at most 2,000 rows; a large first pass, or a pass that ran into its 45-second limit, finishes over the next passes, a second apart. A row the database rejects is named in the log and does not hold up the others. Every node of the cluster runs the same idempotent sync, so losing one does not stop the zone.

A claim or a release is in DNS about a minute after it is in a block, plus the 300-second record TTL. Check a name with `dig @<nameserver> alice.nodes.stagenet.orama.network`, or read it from the chain with `orama chain query orama.nodes.v1.Query/NodeByName '{"name":"alice"}'`.

## Troubleshooting

**DNS not resolving.**

1. Is CoreDNS running? `sudo orama node status` on the node.
2. Logs: `sudo orama node logs coredns -f`.
3. Is port 53 open (TCP and UDP)? `sudo ufw status`, and your provider's firewall.
4. Test locally: `dig @localhost <base-domain>`.

**Glue not propagating.** For a whole registered domain, glue is stored at the registry and can take up to 48 hours; confirm at your registrar it saved. For a subdomain, glue is an ordinary A record in the parent zone; check it is not proxied. A slot does not move because a heartbeat was missed. It moves when its holder is removed with `orama node remove`, or when that node's public address changes. If a glue record names an address that no longer answers, run `orama node dns delegation --env <env>` and update the parent zone.

**A node name does not resolve.** Is `dns.node_names_zone` set (a sub-zone of the base domain) on a node of the cluster whose nameservers answer the zone, and does `sudo orama node logs node` show `Started node names sync`? `Node names sync failed` names the cause: the chain not reachable from the node (the node must have the global layer next to it), or the registry not ready. A name whose node has no literal public IP among its endpoints has no record, and `Node name not published` says when an address, a reserved name or a name that another record already holds was refused. `Node name removals held back` means the chain node is catching up, or a pass reached its bound.

**SERVFAIL.** Usually CoreDNS configuration: check the Corefile syntax, RQLite connectivity and firewall rules. A zone with no SOA yet (no slot has glue) answers SERVFAIL rather than inventing one.

## Security

Only expose what is needed: `ufw allow 53/tcp` and `ufw allow 53/udp`. The generated Corefile does not enable CoreDNS's `health` or `prometheus` plugins, so there are no extra ports. The recursive block for non-authoritative queries answers only loopback clients (an `acl` allowing `127.0.0.0/8` and `::1`), so the node cannot be used as an open resolver. Consider rate limiting to blunt DNS amplification; that goes in the Corefile.

When running several nameservers: they share one RQLite cluster, so DNS records synchronise automatically; all must use the same `--base-domain`; install them in order, one at a time; and re-run `orama node dns delegation --env <env>` whenever the set changes.
