# Security

The Orama Network implements defense-in-depth security across network, authentication, data storage, and process isolation layers. This page covers the security architecture and hardening measures that protect your node and the cluster.

## Network Isolation

### WireGuard Mesh

All inter-node communication travels over an encrypted WireGuard VPN mesh (`10.0.0.0/24`). No cluster ports are exposed publicly — only SSH (22), HTTPS (443), and WireGuard (51820). The Tor client's SOCKS5 proxy (9050) binds to `127.0.0.1` only, and Tor opens no inbound port.

Internal services (RQLite, Olric, IPFS, Gateway) bind to WireGuard IPs and are unreachable from the public internet.

### IPv6

IPv6 is disabled system-wide to prevent services bound to `0.0.0.0` from being reachable via IPv6, which would bypass the IPv4 firewall rules.

### CIDR Enforcement

The WireGuard subnet uses a strict `/24` mask across all components (firewall, rate limiter, auth module, iptables rules). This prevents other tenants on shared VPS providers from reaching cluster services via overlapping `10.x.x.x` address ranges.

## Authentication

### Wallet-Based Auth

Client authentication uses cryptographic wallet signatures (EVM via RootWallet, Solana via Phantom):

1. Client requests a challenge nonce
2. Client signs the nonce with their wallet private key
3. Server verifies the signature and issues a JWT
4. JWT is used for subsequent requests (15-minute expiry, refresh token support)

### API Keys

API keys provide long-lived credentials scoped to a namespace. Keys are stored as **HMAC-SHA256 hashes** using a server-side secret — the raw key is never stored in the database and is only shown once at creation time. Save it securely.

### Refresh Tokens

Refresh tokens are stored as **SHA-256 hashes**. If the database is compromised, attackers cannot use the hashes to impersonate users.

### Internal Service Auth

All internal services require authentication:

- **RQLite** — HTTP basic auth on all queries and writes
- **Olric** — Memberlist gossip encrypted with a shared 32-byte key
- **IPFS Cluster** — TrustedPeers restricted to known cluster peer IDs
- **Internal WG endpoints** — Cluster secret required for peer management
- **Vault** — Guardians require a session token and an Ed25519 ownership signature on every share read and write; the guardian port is reachable only over WireGuard (see [Vault guardians](/docs/operator/vault-guardians))
- **WebSockets** — Origin header validated against the node's domain

## Data Protection

### At Rest

- **TURN secrets, function secrets, push tokens, deployment env, agent tokens** encrypted with AES-256-GCM. The key is HKDF of `secrets/encryption-root` (starts as a copy of the cluster secret). `orama operator rotate-secrets --rotate` replaces the IKM without touching IPFS-Cluster or the mesh bearer
- **OramaOS nodes** — Full-disk LUKS2 encryption with Shamir key distribution (see the OramaOS page)
- **Refresh tokens and API keys** — Stored as cryptographic hashes, not plaintext

### In Transit

- **Client ↔ Gateway** — TLS 1.3 via Caddy with automatic ACME certificates
- **Node ↔ Node** — WireGuard (ChaCha20-Poly1305)
- **Olric gossip** — Memberlist encryption key
- **Node join** — TOFU certificate pinning (CA fingerprint embedded in invite token)

## Process Isolation

### Dedicated User

All services run as the `orama` user instead of root. Services that need privileged ports (Caddy on 80/443, CoreDNS on 53) use Linux capabilities (`CAP_NET_BIND_SERVICE`) instead of running as root.

### systemd Hardening

Every service unit includes security directives:

```
ProtectSystem=strict       — read-only filesystem except explicit paths
ProtectHome=yes            — no access to /home
NoNewPrivileges=yes        — cannot escalate privileges
PrivateDevices=yes         — no access to physical devices
ProtectKernelTunables=yes  — cannot modify kernel parameters
ProtectKernelModules=yes   — cannot load kernel modules
RestrictNamespaces=yes     — cannot create new namespaces
ReadWritePaths=/opt/orama/.orama  — only writable path
```

### OramaOS Sandboxing

On OramaOS nodes, services get additional isolation via Linux namespaces and seccomp:

- **Mount namespace** — each service only sees its own data directory as writable
- **UTS namespace** — isolated hostname
- **Seccomp filtering** — per-service syscall allowlist (e.g., RQLite gets fsync/fdatasync for WAL, Gateway gets sendfile for HTTP)

## Supply Chain Security

### Binary Signing

Nodes install only build archives signed by an address they trust. The list of trusted addresses (the trust anchor) is `/etc/orama/archive-signers` on every node, and there is no unsigned mode, no source-build mode and no built-in signer: a cluster trusts its operator's wallet. The archive's manifest lists the SHA-256 of every file, and the signature covers the manifest. Unsigned, tampered or wrongly signed archives are rejected before anything under `/opt/orama` changes. See [Signed archives](/docs/operator/signed-archives).

### OramaOS Image Signing

OramaOS images are signed with the same rootwallet. The agent verifies signatures before applying A/B partition updates. Failed signature verification prevents the update from being installed.

### dm-verity

The OramaOS image can carry dm-verity hashes for the root filesystem, but dm-verity is not wired at boot today, so rootfs integrity is not enforced. See [OramaOS](/docs/operator/orama-os).

## WebSocket Security

All WebSocket upgraders validate the `Origin` header against the node's configured domain. This prevents cross-site WebSocket hijacking — a malicious webpage cannot open a WebSocket connection to your Orama node on behalf of a logged-in user.

Non-browser clients (which don't send an Origin header) are still allowed.

## WebRTC Security

- **SFU binds only to WireGuard IPs** — never exposed on public interfaces
- **Forced relay mode** — `iceTransportPolicy: relay` enforced server-side, preventing direct peer connections
- **HMAC credentials** — Per-namespace TURN shared secrets. REST and host-function credentials last 24h (they are minted once per call and not refreshed); credentials the SFU hands out on the signaling socket use the per-namespace TTL, 600s by default, and are refreshed
- **TURN secrets encrypted at rest** — AES-256-GCM in the database

## Secrets Management

Cluster secrets are stored in `/opt/orama/.orama/secrets/`:

| Secret | Purpose |
|--------|---------|
| `cluster-secret` | Cluster identity, used for internal endpoint auth |
| `rqlite-password` / `rqlite-auth.json` | Written at genesis; `rqlited` starts with `-auth` and every client (node, gateway, CLI, installer) sends the `orama` user and this password |
| `api-key-hmac-secret` | HMAC key for API key hashing |
| `olric-encryption-key` | Olric memberlist gossip encryption |

These are generated at cluster genesis and distributed to joining nodes via the encrypted join response over WireGuard.

### RQLite HTTP auth

`rqlited` starts with `-auth`, so its HTTP API answers 401 to any request without the credentials in `rqlite-auth.json`. It binds only the node's WireGuard advertise address (`discovery.http_adv_address` in `node.yaml`, for example `10.0.0.1:10100`), never loopback and never a public interface, and ufw does not open the port. Namespace instances bind the `HTTP_ADDR` in their `/var/lib/orama-unit-env/<ns>/rqlite.env`. A 401 during a mixed-fleet upgrade means an old binary without the credentials is talking to a new `rqlited`; see [Troubleshooting](/docs/operator/troubleshooting#6-rqlite-returns-401-unauthorized).

## Security Checklist for Operators

After setting up a node, verify:

1. `ss -tlnp` — only expected ports are listening (22, 53, 80, 443, 51820)
2. `ss -tlnp6` — no IPv6 listeners
3. `ufw status` — incoming is `deny (default)` and the RQLite ports are not in the allow list
4. `wg show wg0` — recent handshakes with all peers
5. `ps aux | grep orama` — services running as `orama` user, not root
6. `orama monitor report --env <env>` — all health checks pass
