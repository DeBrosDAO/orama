# Upgrades

A new Orama version is a new **signed archive** and a **rolling restart**. Extract can happen on every node at once. Restarts happen **one node at a time**, with a health check between each. A cluster can also be set to fetch published releases and roll them out itself, one node at a time ([Automatic updates](#automatic-updates)). This page is the protocol, the commands, and the traps.

> **Never restart all nodes at once.** The registry database (index RQLite) is a Raft group and needs a majority of its voters. Stopping two of three loses quorum and takes the cluster down.

## The short version

```bash
orama upgrade --dry-run          # what each node runs, what it will run, and in what order
orama upgrade                    # show the plan, ask, then roll
orama upgrade --yes              # roll without asking
orama upgrade --node 203.0.113.11   # one node only
```

`orama upgrade` takes the **newest signed release of your network's channel**. The channel is the release repository and channel your network's manifest names (`orama network list` shows the network; stagenet follows `nightly`). The release is verified on your machine against the release root built into the CLI before anything is sent: the signed metadata, then the archive's length and hashes. Every node verifies it again, against the release root it adopted, before it replaces a file. An environment that is on no network of the registry (a cluster you added by its gateway) has no channel; `orama upgrade` says so and points at `orama maint rollout`, which builds and rolls your own archive (below).

The plan is a table, one row per node, in the order the rolling upgrade will restart them:

```text
Network stagenet, channel nightly: newest release 0.3.1

NODE         ROLE                  RUNNING  TARGET  ACTION   GLOBAL LAYER
203.0.113.10 Follower, nameserver  0.3.0    0.3.1   upgrade  refreshed after the node
203.0.113.12 Follower, nameserver  0.3.0    0.3.1   upgrade  -
203.0.113.11 Leader, nameserver    0.3.0    0.3.1   upgrade  -

3 of 3 nodes will be restarted one at a time, with a health and quorum check between nodes.
```

- **RUNNING** is what the node's own report says, the same telemetry `orama status` shows (sign in with `orama auth login`, or add `--ssh` to read every node over SSH). A node that sent no report is `unknown` and is upgraded.
- **ACTION** is `upgrade` for an older node, `current` for one already on the release (left alone; `--reinstall` puts the release in place on it again), and `ahead` for a node on a newer release than the channel's, which is never downgraded.
- A node that cannot be read, or a cluster with no single leader, refuses the plan: an unreachable node is never assumed healthy.

After you confirm (or with `--yes`), the release is **staged on every node first**, four at a time, which restarts nothing: the archive, its signed metadata and the release root go to a private directory on each node, and the node's installed CLI stages it on the release root's checks alone (`orama maint node stage-archive --release-only`). The root is adopted only on a node that has none; a node that trusts another root refuses the release. If any node refuses, nothing has been restarted and the command says which. Then the rolling upgrade below runs, one node at a time behind its health and quorum gate. **A node that has the global layer** also refreshes it right after its own upgrade and before the gate: the global binaries (`orama`, `orama-global`, `ipfs`) are replaced from the release, all of them checked against its manifest before the first is written, and only the running services whose process still executes a replaced file are restarted (the provider, archiver, indexer, repair delegate and reporter run `orama-global`, the public Kubo `ipfs`, the onion service's gate `orama`). The test is the process, not what this run replaced, so a refresh that was interrupted is finished by running it again; a service that is stopped stays stopped. The chain and the Tor relay or directory authority are not restarted by it.

**The chain binary (`oramad`) is never swapped by an upgrade.** When the release carries an `oramad` other than the one cosmovisor runs, the node reads the chain's scheduled upgrade plan: with a governed plan it stages the release's `oramad` and shielded verifier for that plan and cosmovisor switches to them at the plan's height (when the plan's info names a checksum for the platform's binary, the release's `oramad` has to be that one, or it is not staged); without a plan it keeps the running `oramad` and prints why. After the proposal passes, `orama upgrade` again stages it.

`orama node upgrade --env` (the remote mode) and `orama node remove` print a notice that they are replaced by `orama upgrade` and `orama remove`; they still work, for scripts. On the node, `sudo orama node upgrade --restart` upgrades that node and is what the rolling upgrade runs.

### Rolling your own build

`orama maint rollout` is the maintainer's path for an archive you built yourself:

```bash
cd orama/core
git pull                                   # the version you want to roll out
orama maint rollout --env mycluster              # build, push, and PRINT the plan
orama maint rollout --env mycluster --yes        # do it
```

`orama maint rollout` builds a signed archive, pushes it to every node, prints the restart plan, and stops unless `--yes` is given. It never reuses an older archive on its own; to roll out a specific one use `--no-build --archive <path>`.

Step by step, with more control:

```bash
orama maint build                                                   # signed with your RootWallet
orama maint push --env mycluster --archive $ARCHIVE                 # upload and verify on every node
orama node upgrade --env mycluster                            # read every node, print the plan
orama node upgrade --env mycluster --yes                      # execute it
orama node upgrade --env mycluster --node 203.0.113.11 --yes  # one node only
orama node upgrade --env mycluster --delay 600 --yes          # allow 10 minutes per node to rejoin
```

You need RootWallet unlocked for the whole run. The CLI touches the agent every five minutes while it holds keys, so one unlock covers a long rollout.

## What `push` does

`orama maint push` uploads the archive from your machine to each node in turn; no node is a hub and no node's SSH key leaves your machine (`--direct` is accepted and changes nothing). On each node it runs the node's **installed** CLI, which, under a lock on `/opt/orama`:

1. extracts into a private directory (regular files and directories only; at most 1024 entries, 512 MiB per file, 4 GiB total)
2. verifies the signature against `/etc/orama/archive-signers`, every file against the signed manifest, and the architecture
3. only then swaps `manifest.json`, `manifest.sig`, `bin/`, `systemd/` and `packages/` into place, and puts everything back if any step fails

A refused archive leaves `/opt/orama` exactly as it was. `push` reaches only installed nodes; a fresh machine gets its first archive from `orama node setup`.

## What the rolling upgrade does

1. **Reads every node's Raft state** over SSH before touching anything.
2. **Prints a plan**: followers first, the leader last, nameservers spaced apart so the zone always has one answering. The order is deterministic, so the plan you approve is the plan that runs.
3. **Refuses to start** if the state does not permit it: no node reports itself leader, two do (an election), or any node's state could not be read. An unreachable node is never assumed healthy.
4. **Requires `--yes`.** Without it nothing restarts.
5. **Runs the staged build's own CLI** on each node (`/opt/orama/bin/orama node upgrade --restart`), never the node's old `/usr/local/bin/orama`, so every step is the new release's code.
6. **Hands over before it stops anything.** While the node still serves, it records the node's Raft identity, checks quorum, sets the maintenance flag, transfers leadership on the index and each namespace RQLite, and confirms another voter leads. If this node is still the leader afterwards, the upgrade aborts and the node keeps serving.
7. **Stops** `orama-node` (the supervisor) first, then every loaded namespace unit.
8. **Gates on the node rejoining** before touching the next: Raft state `Leader` or `Follower`, a leader known to exist, an applied index within 200 entries of the leader's commit index, and the gateway answering `/health`. `--delay` (default 300 seconds) is the budget for this gate, not a sleep between nodes.
9. **Stops the rollout** the moment a node fails the gate, leaving the remaining voters untouched.

Then the node restarts its other units in order: namespace RQLite, Olric, gateway, everything else. Sample plan (the first column is each node's public address; the second is the role recorded for it in the environment):

```text
Rolling upgrade plan (3 nodes, 3 nameservers):

  1. 203.0.113.10     nameserver             follower (nameserver — spaced so the zone keeps answering)
  2. 203.0.113.12     nameserver             follower (nameserver — spaced so the zone keeps answering)
  3. 203.0.113.11     nameserver             leader — last, after leadership transfer

Each node is upgraded only after the previous one reports Leader or Follower,
an applied index caught up to the leader, and a gateway serving /health.
```

### The quorum guard

`stop`, `restart` and the pre-upgrade step refuse to run when stopping this node would cost the registry its quorum, and print the arithmetic: `Quorum check: 3/3 voters reachable, 2 would remain (need 2).` Quorum is a majority of the **configured** voters. Stopping a node does not remove it from the Raft configuration, so on three voters you may stop one, and on two voters you may stop neither. The guard fails closed: if it cannot read the status, it refuses. `orama node stop --force` and `orama node restart --force` skip it. Use them only when you have confirmed the remaining voters can still form a quorum. The pre-upgrade step has no override of its own: when it aborts, it tells you to use `orama node stop --force`. (`orama node upgrade --force` is a different flag: it reconfigures all settings.)

## During a rolling upgrade

- **Pause namespace and deployment create and delete.** Coordination between nodes needs a message authentication code signed for the receiving node (and, on this release, for the port of the process it is for), and a node on the old build cannot coordinate spawns, teardowns or replica operations with a node on the new one until every node is upgraded. Such requests are refused with 401 or 403. The previous stamps (the coordination v2 stamp, and the unnonced node-API and certificate-challenge stamps) are still accepted while any registered node has not reported that it signs the nonced ones, and every node writes them too, so only a build older than those is affected. Once every node reports it, the previous stamps are refused and no longer written. A node rolled back to an older build counts as not signing the nonced stamps again from its next heartbeat, and a node that is down and was never removed keeps the previous stamps accepted: remove dead nodes with `orama node remove`. Network status, telemetry and `orama status` keep working across versions. After the last node is upgraded, check that `namespace_pending_cleanup` drains: a teardown refused in the window is recorded there and replayed.
- **The WireGuard peer routes are gone.** `/v1/internal/wg/peer`, `/peers` and `/peer/remove` are not registered on an upgraded node: they answer exactly as a path that never existed does (404 with a valid credential, 401 without one). Nothing calls them, so a mixed fleet needs no handling.
- **Do not add a node** until every cluster you are upgrading is on the same version (see RQLite below).
- **Do not upgrade voters in parallel by hand.** Never `systemctl stop orama-node` on several nodes at once.

## Schema migrations

The gateway embeds SQL migrations. The highest-numbered one is the schema version that gateway **requires**: it refuses to start if that schema is not applied. Migrations take a cluster-wide lock (`cluster_locks('schema-migrations')`), so gateways starting together do not each run the pending list. Check and apply:

```bash
sudo orama maint node schema status      # required vs applied version, and pending migrations
sudo orama maint node schema apply       # apply pending migrations to the local RQLite
```

A namespace owner can check drift without SSH with `GET /v1/schema-status`.

## Bundled service versions

The archive bundles RQLite 10.4.0, IPFS Kubo v0.43.1, IPFS Cluster v1.1.6, Olric v0.7.4 and Caddy 2.11.4; ntfy 2.28.0 is pinned in its installer; Node.js 24.21.0 LTS (for Node.js, Next.js SSR and npm deployments) is downloaded at install and upgrade and verified against a pinned digest. The build refuses a Kubo or RQLite tarball whose SHA-256 differs from the pinned digest.

**The RQLite v10 upgrade is one way.** On its first start a v10 `rqlited` converts the node's snapshots into its own format and deletes the old ones. A v10 node cannot join a v9-or-older cluster, and a node that has started under v10 cannot go back; a downgrade is a restore from backup into a new cluster. Take a backup first. Roll it node by node and finish **every** cluster before adding a node: the index cluster, then each namespace cluster. During the roll the cluster is mixed v9 and v10 and that works.

## Back up the registry first

The index RQLite is backed up hourly by the leader, to the leader's local disk and encrypted and pinned into IPFS, with its CID, SHA-256 and size recorded in `rqlite_backups`. Retention is 24 hourly plus one a day for 7 days. A backup on the leader's own disk protects against little; the pinned copy is the one that matters. **A backup is only as good as the last time someone restored it:** exercise a restore on a scratch cluster, not for the first time during an incident.

## Changing the certificate authority

`orama node upgrade --env mycluster --acme-ca letsencrypt --yes` upgrades every node and records the new CA. See [TLS and certificates](/docs/operator/tls-certificates#changing-a-running-cluster-s-ca).

## A node that boots without quorum

A node that cannot reach a Raft leader does not exit. It starts everything that needs only the local machine (WireGuard, IPFS, the local RQLite replica, CoreDNS, the gateway, Caddy, tenants), reports its lifecycle state as `degraded`, and keeps retrying the cluster half in the background. When quorum returns it goes `active` with no restart. So a `degraded` node is serving. Check which components have not converged before reaching for a recovery command:

```bash
sudo orama node logs node -n 100 | grep "Boot component"
```

Only escalate to `recover-raft` when the **whole cluster** is leaderless.

## Checking health between nodes

After every node (the rollout does this for you, but when you do it by hand):

```bash
orama status report --env mycluster --node 203.0.113.11    # that node: services, RQLite state, WireGuard peers
orama status report --env mycluster                         # the cluster: leader stable, quorum, mesh, indices in sync
```

Carry on only when both pass. If a node shows problems, investigate; do not skip it and hope.

## Recovering a split cluster

If nodes are stuck in `Candidate` or report "leader not found":

```bash
orama maint node recover-raft --env mycluster
```

**One node's data is kept. Every other node's Raft log and database are deleted. Nothing is backed up.** The command reads every node's applied index, keeps the one furthest ahead, prints what each reported and asks you to confirm. `--leader <ip>` names the node whose data to keep; `--leader-raft-addr <wg-ip>:10101` is for when RQLite is not answering anywhere. It resets the kept node to a single-member cluster, confirms it comes back as Leader before touching any other node, wipes the others, and starts them one at a time, each pulling a full snapshot. Take a backup yourself first if the surviving node might not be the right one.

## Automatic updates

A cluster can keep itself on a release channel. It does nothing until you tell it where releases are. These are cluster settings, changed by an operator and written to the audit trail:

```bash
orama maint cluster settings set release-repo https://releases.example.org/tuf
orama maint cluster settings set update-channel stable            # stable (the default) or nightly
orama maint cluster settings set update-window 1-5                # hours UTC when auto may install; empty is any hour
orama maint cluster settings set auto-update notify               # off, notify (the default) or auto
orama maint cluster settings show
```

Every node runs `orama-autoupdate.timer`, which runs `orama maint node autoupdate run` as root 10 minutes after boot and then every 15 minutes (you can run it by hand; it does the same). The agent does nothing, and says why, until the cluster has a `release-repo` and the node has adopted a release root. A cluster installed with `orama node setup --release` has the root on every node; for any other node, `sudo orama node trust add-root root.json` adopts one, as does installing an archive built with `orama maint build --release-root`.

Each run fetches the channel's metadata and verifies it against the adopted root (every role at its threshold, an unexpired timestamp, a snapshot not older than the newest the node has seen, and the channel's own keys for its own files). What does not verify is refused, shown by `orama status` as a warning, and never installed.

- **`notify`** (the default): a newer verified release is shown by `orama status` as information. Nothing is installed.
- **`auto`**: the node installs it, but only when the cluster is not degraded and a majority of the Raft voters are up, the hour is inside `update-window`, no node has failed that release, and it is this node's turn. The turn is the rollout plan: followers first, the leader last, nameservers spaced, **one node at a time**, under a cluster-wide lock. A downgrade is refused.
- **A validator** (a machine that runs the chain) is never `auto`; its chain binary is changed by hand. On `auto` its agent writes a refusal notice saying so, records the release as `skipped`, and exits 0; the rollout counts a skipped node as done and moves on to the next.

An install is `orama maint node stage-archive --release-only` (which keeps the release it replaces), then that release's `orama node upgrade --restart`, then a health gate: Raft `Leader` or `Follower`, a leader known, an applied index within 200 of the commit index, and the gateway serving. If the upgrade or the gate fails, the previous release is put back and the node is upgraded onto it again. The release is then marked bad for the whole cluster, so the rollout stops: no other node tries it, and `orama status` warns. A newer release supersedes a bad one. If a run is killed in the middle of an install, the next run finishes or rolls back first, before it reads the policy. A release that could not start installing on a node (a check refused before anything stopped) is not downloaded again every 15 minutes: the node waits 15 minutes, then doubles the wait after each failure, up to 12 hours, and the notice in `orama status` says when the next try is (the record is `/var/lib/orama-autoupdate/install-retry.json`; a different release is not held back, and an install that succeeds clears it). A failure that cannot be written to the registry right after the rollback is kept in the install intent, and the next run records it instead of installing the release again. Each run first removes the fetch directories a killed run left in `/var/lib/orama-autoupdate`.

`orama maint node autoupdate --current <ver> --candidate <ver>` only answers what the policy would do for values you give it, and changes nothing.

The install keeps the release it replaced beside the new one (hundreds of megabytes under `/opt/orama`), and nothing checks free space first. The full behaviour is in the repository's `docs/DEV_DEPLOY.md`, "Auto-update".

## Versions and first upgrades

- The first upgrade from a 0.122.x cluster needs `orama maint push --trust-signers <your address>` because those nodes have no trust anchor, and must run this release's code from your checkout, not the old CLI. The index Raft port moves from 7001 to 10101; one node's address may change at a time with every other voter up, which the one-node-at-a-time rollout guarantees. A cluster of one reforms with `orama maint node recover-raft --leader-raft-addr <wg-ip>:10101`.
- After upgrading from 0.122.x, rotate the index gateway's signing key on every node, one node at a time, after the whole fleet is upgraded. `orama maint operator rotate-signing-key` has no node flag: it calls the gateway of the active environment (or of `ORAMA_API_URL`), and the index gateway that answers rotates its own key. The index gateway's signing keys are now systemd credentials (`/var/lib/orama-gateway-keys/index`, root `0400`), but the key carried over from the old layout was readable by every tenant gateway, and the index key signs for any namespace. Nobody is signed out.
- Access tokens issued before a node's upgrade stop verifying on that node; clients get a 401 and refresh (refresh tokens are registry rows, so they survive), or log in again.
