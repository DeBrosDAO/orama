# OramaOS

OramaOS is a custom minimal Linux image purpose-built for running Orama nodes. It is in development and not yet running on any network: today devnet and testnet nodes run Ubuntu. When finished, it replaces the Ubuntu deployment with a locked-down system where operators cannot access node data.

## Why OramaOS?

Standard Ubuntu nodes give operators root access — meaning they can read all stored data, modify binaries, or tamper with the system. OramaOS eliminates this attack surface:

| Feature | Ubuntu | OramaOS |
|---------|--------|---------|
| SSH access | Yes | No |
| Shell access | Yes | No |
| Disk encryption | No | LUKS2 (Shamir) |
| OS updates | Manual rolling upgrade | Automatic signed A/B swap |
| Service isolation | systemd only | Namespaces + seccomp |
| Rootfs integrity | None | dm-verity hashes exist in the image; not wired at boot, so not enforced today |
| Binary signing | Optional | Required |
| Operator data access | Full | None |

Sandbox clusters remain on Ubuntu for development convenience.

## How It Works

OramaOS is built with Buildroot — a minimal Linux containing only systemd, cryptsetup, WireGuard (built into the 6.6 LTS kernel), and the **orama-agent**. The agent is the only root process and manages everything.

### Partition Layout

```
/dev/sda1 — rootfs-A (SquashFS + dm-verity, read-only)
/dev/sda2 — rootfs-B (standby partition for updates)
/dev/sda3 — data (LUKS2 encrypted, ext4)
```

The root filesystem is a read-only SquashFS. dm-verity can be built into the image, but it is not wired at boot, so rootfs integrity is not enforced today. All mutable state lives on the LUKS-encrypted data partition.

The GPT image as built by genimage (`os/buildroot/board/orama/genimage.cfg`) places the ESP (systemd-boot and kernel) first, followed by rootfs-A, rootfs-B and data, which does not match the device paths the agent operates on (`/dev/sda1`, `/dev/sda2`, `/dev/sda3`). That inconsistency is unresolved in the current code.

The boot flow is systemd-boot, then the rootfs, then orama-agent, then WireGuard, then the services. The orama-agent is the only root process. It manages the boot sequence and LUKS key reconstruction, the WireGuard tunnel, service lifecycle in sandboxed namespaces, commands received from the Gateway over WireGuard, and OS updates (download, verify signature, A/B swap, boot counting).

## Enrollment

OramaOS nodes join the cluster through an enrollment flow (replacing `orama node install`):

### 1. Flash the Image

Download the OramaOS image and flash it to your VPS via your hosting provider's custom image upload (Hetzner, Vultr, OVH, etc.).

### 2. First Boot

On first boot, the agent enters enrollment mode:
- Generates an 80-bit registration code (20 hex characters)
- Prints it on the console TTY (not the journal)
- Opens a temporary HTTP server on port 9999 and waits for a payload sealed under that code

The code is not served over the network: a `GET` on port 9999 used to return it. The Gateway proves it holds the code and sends the cluster configuration encrypted under it, so a wrong code fails at the node and configures nothing.

Each node mints its own agent token during enrollment. The Gateway presents it on every later command, and the agent's command receiver binds only the node's overlay address. A node enrolled before agent tokens existed keeps running its services but accepts no commands until it is re-enrolled.

### 3. Enroll from CLI

On your local machine with the `orama` CLI and rootwallet:

```bash
# Generate an invite token on any existing cluster node
orama node invite --expiry 24h

# Enroll the new OramaOS node — --code is printed on the node's console
orama node enroll \
  --node-ip <vps-public-ip> \
  --code <registration-code> \
  --token <invite-token> \
  --gateway <gateway-url>
```

The CLI sends the console code, invite token and public node IP to the Gateway, which assigns a WireGuard IP and pushes cluster config sealed under the code. The node configures WireGuard, LUKS-encrypts the data partition, and splits the LUKS key via Shamir across peer vault-guardians. Port 9999 closes permanently after enrollment.

### 4. Verify

```bash
orama monitor report --env <env>
```

## LUKS Encryption

The data partition is encrypted with LUKS2 (AES-XTS-Plain64). The encryption key is never stored on the node itself — it's split into shares and distributed across peer vault-guardians using Shamir's Secret Sharing over GF(256).

### Normal Reboot

When an enrolled node reboots:

1. Agent starts, brings up WireGuard
2. Contacts peer vault-guardians over WireGuard
3. Fetches K shares (threshold = max(2, floor(N/3)))
4. Reconstructs the LUKS key via Lagrange interpolation
5. Decrypts and mounts the data partition
6. Zeros the key from memory
7. Starts all services

If not enough peers are available, the agent retries the share fetch with exponential backoff (1s, 2s, 4s, 8s, 16s, at most 5 retries). If reconstruction still fails, it falls back to genesis unlock mode and waits for a manual operator unlock on port 9998 (see [Genesis Node](#genesis-node)).

### Genesis Node

The first OramaOS node in a cluster is the genesis node. It needs a special path because there are no peers yet for Shamir key distribution. **Most of this path is not yet implemented.**

What works today: when Shamir reconstruction fails after a reboot (the genesis node, or peers offline), the agent falls back to **genesis unlock mode**. It starts an HTTP server on the WireGuard interface (port 9998) and waits for the operator to supply the raw LUKS key:

```bash
curl -X POST "http://<wg-ip>:9998/v1/agent/unlock" \
  -H "Content-Type: application/json" \
  -d '{"key":"<base64-encoded 32-byte LUKS key>"}'
```

Not yet implemented (do not rely on any of this):

- **Genesis enrollment.** Enrollment always tries to distribute Shamir shares and fails with "no peers available for key distribution" when the cluster has zero peers. There is no genesis fallback in the enrollment flow, so a genesis OramaOS node cannot currently complete enrollment.
- **Key escrow.** The agent never creates or stores a rootwallet-encrypted copy of the LUKS key, and serves no `GET /v1/agent/genesis-key` endpoint.
- **`orama node unlock --genesis --node-ip <wg-ip> --key-file <path>`.** `--key-file` is required, and it must hold a rootwallet-encrypted LUKS key. Nothing currently produces the key file, so the flow is not usable end to end. The missing piece is key escrow, not the CLI.
- **The 5-peer transition.** No agent code distributes Shamir shares once 5 or more peers join, deletes a local escrowed key, or transitions to normal Shamir-based unlock.

Until this is built, operators must record the genesis node's raw LUKS key out of band during initial enrollment and supply it manually to unlock the node after a reboot.

## Node Management

Since OramaOS has no SSH, all management goes through the Gateway API, which proxies requests to the agent over WireGuard (port 9998). The agent is never directly accessible from the public internet. Status, command, logs and leave require an **admin** API key (or owner JWT); pass it as `Authorization: Bearer <admin-api-key>`. `service` on logs is an allowlist: `rqlite`, `olric`, `ipfs`, `ipfs-cluster`, `gateway`, `coredns` and `agent`.

### Check Status

```bash
curl "https://gateway.example.com/v1/node/status?node_id=<id>"
```

### Restart a Service

```bash
curl -X POST "https://gateway.example.com/v1/node/command?node_id=<id>" \
  -H "Content-Type: application/json" \
  -d '{"action":"restart","service":"rqlite"}'
```

### View Logs

```bash
curl "https://gateway.example.com/v1/node/logs?node_id=<id>&service=gateway&lines=100"
```

### Graceful Departure

```bash
curl -X POST "https://gateway.example.com/v1/node/leave" \
  -H "Content-Type: application/json" \
  -d '{"node_id":"<id>"}'
```

This stops services on the node and removes the WireGuard peer. Shamir share redistribution is not implemented. There is no `orama node leave` CLI subcommand.

## Automatic Updates

OramaOS uses an A/B partition scheme for safe, automatic updates:

1. Agent checks for new versions hourly against a central update server (`https://updates.orama.network/v1/latest`)
2. Downloads the signed image over HTTPS
3. Verifies the SHA-256 checksum and the rootwallet EVM signature against the embedded public key
4. Writes to the standby partition (if running from A, it writes to B)
5. Sets systemd-boot to boot the standby with boot counting enabled (`tries_left=3`)
6. On the next reboot the node boots into the new partition. The agent does not reboot automatically
7. If the new version boots successfully (agent starts, WireGuard connects, services healthy): marked as "good"
8. If it fails 3 times: systemd-boot rolls back to the previous version

Updates are staged automatically; activating one requires a reboot. Failed updates are automatically rolled back.

## Service Sandboxing

Each service runs in its own isolated environment:

- **Mount namespace** — only the service's data directory is writable; everything else is read-only
- **UTS namespace** — isolated hostname
- **Dedicated UID/GID** — each service runs as a different non-root user
- **Seccomp filtering** — per-service syscall allowlist, currently running in **audit-only mode**: disallowed syscalls are logged, not blocked. Enforcement (killing the process on a disallowed syscall) is not yet enabled.

| Service | Writable Path | Extra Syscalls Allowed |
|---------|---------------|----------------------|
| RQLite | `/opt/orama/.orama/data/rqlite` | fsync, fdatasync, ftruncate, rename (Raft + SQLite WAL) |
| Olric | `/opt/orama/.orama/data/olric` | sendmmsg, recvmmsg (memberlist gossip) |
| IPFS | `/opt/orama/.orama/data/ipfs` | sendfile, splice (data transfer) |
| Gateway | `/opt/orama/.orama/data/gateway` | sendfile, splice (HTTP serving) |
| CoreDNS | `/opt/orama/.orama/data/coredns` | sendmmsg, recvmmsg (DNS) |

## Factory Reset

OramaOS nodes cannot be wiped with `orama node wipe` (or the deprecated `orama node clean`): there is no SSH. Options:

- **Graceful departure:** Use the `/v1/node/leave` API endpoint. It stops services on the node and removes the WireGuard peer
- **Cluster-side removal:** once the node is gone, `orama node remove --env <env> --node <ip> --offline` takes it out of raft, every namespace it served and the node registry from a survivor. `--offline` is required: the command never tries to reach an OramaOS node
- **Factory reset:** Reflash the OramaOS image via your hosting provider's dashboard
- **Data is unrecoverable:** LUKS key is distributed across peers — reflashing destroys all data permanently

## Troubleshooting

### Enrollment doesn't complete

Read the registration code from the node's console (`--code` is required; it is not served on port 9999). Check that port 9999 is open in your VPS provider's external firewall (Hetzner firewall, AWS security groups). There is no WebSocket enrollment path.

### LUKS unlock fails after reboot

Not enough peer nodes are online. The node needs at least K peers reachable over WireGuard (K = max(2, floor(N/3))). Ensure cluster nodes are running. For the genesis node, which has no peers to reconstruct shares from, unlock it manually (see [Genesis Node](#genesis-node)).

### Update rolled back

Check agent logs via `GET /v1/node/logs?service=agent`. Common causes: corrupted download (signature check should catch this), hardware issue, or incompatible configuration.

### Node stuck in enrollment mode

The node boots but enrollment never completes. Check that you can reach `http://<vps-ip>:9999/` from your machine. If not, the VPS provider's firewall may be blocking port 9999: OramaOS opens it through its internal firewall, but external provider firewalls must be configured separately.

### Services unhealthy after reboot

Use `GET /v1/node/status` to identify which services are down, then try restarting: `POST /v1/node/command` with `{"action":"restart","service":"<name>"}`.
