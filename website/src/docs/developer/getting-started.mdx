# Quickstart

This takes you from nothing to a deployed site and a working database call. It assumes someone runs an Orama cluster you can reach (your own, see [Install a cluster from scratch](/docs/operator/install-from-scratch), or one you were given access to). You need its gateway URL, for example `https://cluster.example.com`.

## 1. Install the tools

```bash
brew install DeBrosDAO/tap/orama      # the CLI
orama version
npm install @debros/orama             # the SDK, in your app
```

You also need a wallet that can sign. Install [RootWallet](/docs/rootwallet/install) (desktop, or the `rw` CLI), create a wallet, and leave it unlocked. Orama has no accounts and no passwords: your wallet address is your identity.

## 2. Tell the CLI which cluster to use

A fresh CLI knows no cluster. Add yours:

```bash
orama env add mycluster https://cluster.example.com
orama env use mycluster
```

`orama env list` and `orama env current` show what is configured. If the cluster uses Let's Encrypt staging certificates, add `--ca-file le-staging.pem` ([TLS and certificates](/docs/operator/tls-certificates#trusting-a-staging-cluster-from-your-cli)).

## 3. Sign in

```bash
orama auth login
orama auth whoami      # asks the gateway who you are and what you may do
orama auth status      # what is stored on this machine (asks nobody)
```

The CLI asks RootWallet to sign a challenge from the gateway. What it stores is a **session**: an access token that lasts 15 minutes and renews itself from a 30-day refresh token. This is the *lobby* sign-in: you are in, but you hold no namespace yet. On a machine with no wallet (a server over SSH, CI), `orama auth login` prints a code, and `orama auth approve <code>` on a machine that has your wallet approves it. See [Sign-in and sessions](/docs/developer/sign-in).

## 4. Create a namespace

A namespace is your own small cluster: a database, a cache and a gateway on three nodes. You own what you create.

```bash
orama namespace create myapp
orama auth login --namespace myapp
```

Creating a namespace does not sign you in to it; the second command does. Some clusters allow only their operators to create namespaces; if yours refuses, ask an operator ([Cluster administration](/docs/operator/cluster-admin#who-may-create-namespaces)). See [Namespaces](/docs/developer/namespaces).

## 5. Deploy something

```bash
mkdir site && echo '<h1>Hello from Orama</h1>' > site/index.html
orama deploy static ./site --name www
orama app list
orama app get www
```

`orama deploy static` publishes a directory as a deployment and prints its URL, a name under the cluster's base domain. Other runtimes: Next.js, Go and Node.js backends ([Deployments](/docs/developer/deployments)).

## 6. Use a database

```bash
orama db create appdb
orama db query appdb "CREATE TABLE notes (id INTEGER PRIMARY KEY, text TEXT)"
orama db query appdb "INSERT INTO notes (text) VALUES ('hello')"
orama db query appdb "SELECT * FROM notes"
```

This is a per-namespace SQLite database, reached from the CLI. The namespace also has a replicated SQL database (RQLite) that your code reaches through the SDK, shown next. See [Databases](/docs/developer/databases).

## 7. Call it from code

What a key may do depends on its grants. Two keys cover a typical app.

**On a server, in CI or in a script:** an `admin` key. It reaches the control plane, including the namespace's RQLite database, so it never goes in a browser or mobile bundle.

```bash
orama namespace keys create --scope admin --label server
```

The command prints the key once, after a short report. Copy the line under `API KEY` into your secret store; it cannot be shown again.

```ts
import { createClient } from "@debros/orama";

const server = createClient({
  baseURL: "https://ns-myapp.cluster.example.com",
  apiKey: process.env.ORAMA_API_KEY,
});

await server.db.createTable("CREATE TABLE messages (id INTEGER PRIMARY KEY, room TEXT, body TEXT)");
await server.db.exec("INSERT INTO messages (room, body) VALUES (?, ?)", ["general", "hi"]);
const rows = await server.db.query("SELECT * FROM messages WHERE room = ?", ["general"]);
```

**In a browser or mobile app:** a key with data-plane grants only, named explicitly. The `app-runtime` profile does not include `pubsub` or `cache`, so ask for them.

```bash
orama namespace keys create --scope invoke,pubsub,cache --label web
```

```ts
const client = createClient({
  baseURL: "https://ns-myapp.cluster.example.com",
  apiKey: process.env.ORAMA_WEB_KEY,      // injected at build time
});

await client.cache.put("sessions", "alice", { seen: Date.now() }, "1h");
await client.pubsub.publish("room:general", "hello");
```

Storage is different: the gateway refuses a key on its own and wants the signed-in user as well, so upload after the user has signed in with their wallet ([Wallet login](/docs/developer/sdk-reference#wallet-login)):

```ts
const { cid } = await client.storage.upload(new Blob(["file contents"]), "hello.txt");
```

Where a key may live, and what each profile can do: [Access control and keys](/docs/developer/access-control). The full client: [TypeScript SDK](/docs/developer/sdk-reference).

## CI and scripts

Set `ORAMA_TOKEN` to an API key or a token. A key is exchanged for a session once per run. Mint the key once on your machine (add `--expires-in-days` to shorten its life, 90 days is the default), put it in your CI system's secret store, and expose it to the job:

```bash
orama namespace keys create --scope admin --label ci      # prints the key once; store it
```

```bash
export ORAMA_TOKEN="$CI_ORAMA_KEY"      # from the CI secret store
orama deploy static ./dist --name www --update
```
