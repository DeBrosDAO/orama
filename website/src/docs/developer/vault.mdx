# Vault

Orama Vault is a zero-knowledge secret storage service built on Shamir's Secret Sharing. It splits secrets client-side and distributes shares across guardian nodes so that no single node ever sees the full secret. Guardian nodes run the `vault-guardian` service, written in Zig, and authenticate requests using HMAC-based challenge-response with per-identity session tokens.

## How It Works

When you store a secret, the SDK performs the following entirely on the client:

1. The secret is split into shares using Shamir's Secret Sharing over GF(2^8) polynomial interpolation.
2. Each share is encrypted and sent to a different guardian node over an authenticated session.
3. The adaptive threshold (minimum shares needed for reconstruction) is calculated automatically from the guardian count.

To retrieve the secret, the SDK collects shares from guardians and reconstructs the original value. Shares are wiped from memory immediately after each operation.

This means:

- **Zero-knowledge** — No single guardian ever sees the full secret.
- **Client-side splitting** — Secrets are split before leaving the client.
- **Fault tolerant** — Secrets survive guardian failures as long as the read threshold is met.
- **Cryptographically secure** — Based on polynomial interpolation over finite fields (GF(2^8)).
- **Write quorum** — A majority of guardians must acknowledge before a write is considered successful.
- **Memory safe** — Shares and keys are wiped from memory after every operation.

## Architecture

The vault has two access paths:

### Gateway Proxy (Client → Gateway → Guardians)

**This is the path for applications.** The Orama gateway exposes V1 vault
endpoints over HTTPS and performs the Shamir splitting and combining
server-side. Each request proves ownership of the identity with a fresh Ed25519
signature.

### Direct (Tooling → Guardians)

Guardians listen on the WireGuard overlay (`10.0.0.x`), so only software running
on the mesh can reach them: node agents, operator tooling and RootWallet. That
client is published separately as `@debros/orama-vault`. It used to ship inside
`@debros/orama`, which offered every application an API it had no route to.

| Path | API Version | Who splits/combines | Auth | For |
|------|-------------|-------------------|------|-----|
| Client → Gateway | V1 | Gateway | Per-request Ed25519 ownership signature | Applications |
| Tooling → Guardians | V2 | Client | Guardian session token | Software on the WireGuard overlay |

## Setup

The direct client is its own package. Install it only where the guardians are
reachable:

```bash
npm install @debros/orama-vault
```

```typescript
import { VaultClient } from "@debros/orama-vault";

const vault = new VaultClient({
  guardians: [
    { address: "10.0.0.1", port: 7500 },
    { address: "10.0.0.2", port: 7500 },
    { address: "10.0.0.3", port: 7500 },
  ],
  identityHex: "your-identity-hex",
  timeoutMs: 5000,
});
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `guardians` | `GuardianEndpoint[]` | Yes | Guardian nodes that hold shares. Each needs `address` and `port`. This list is the unit of redundancy: a secret is split into one share per guardian listed, and the write quorum is computed from its size. |
| `identityHex` | `string` | Yes | Your identity in hex. Scopes the secrets and names the session. |
| `timeoutMs` | `number` | No | Request timeout in milliseconds per guardian. |

## Storing Secrets

Pass a name, the secret as a `Uint8Array`, and a version number:

```typescript
const data = new TextEncoder().encode("my-secret-data");
const result = await vault.store("api-key", data, 1);

console.log(result.ackCount);         // number of successful writes
console.log(result.totalContacted);   // guardians the write was addressed to
console.log(result.failCount);        // number of write failures
console.log(result.guardianResults);  // per-guardian results
```

A write that does not reach quorum throws a `QuorumError` carrying `ackCount`,
`required` and the per-guardian results, so anything `store` returns is durable.
It used to resolve with `quorumMet: false`, which a caller who did not inspect
that field — the obvious way to use a promise that resolves — read as success.

### Secret Name Constraints

| Constraint | Limit |
|-----------|-------|
| Allowed characters | Alphanumeric, `_`, `-` |
| Max name length | 128 characters |
| Max secrets per identity | 1,000 |
| Max secret size | 512 KiB |

## Retrieving Secrets

The SDK automatically gathers the minimum number of shares from guardians and reconstructs the original value:

```typescript
const retrieved = await vault.retrieve("api-key");

console.log(new TextDecoder().decode(retrieved.data)); // "my-secret-data"
console.log(retrieved.sharesCollected);                // number of shares used
console.log(retrieved.version);                        // the version returned
```

Reconstruction requires at least the read threshold number of shares, calculated
automatically from the guardian count.

Shares are grouped by the version they belong to and only shares of one version
are ever combined. A guardian that missed the last write still answers, with a
share of the previous split; mixing it with newer shares reconstructs neither
version and raises no error. If the newest version is short of the threshold —
a write that did not reach quorum — the newest version that is complete is
returned, and `version` says which. When no version has enough shares,
`retrieve` throws a `QuorumError` naming what it collected.

## Listing Secrets

List all secrets stored under your identity:

```typescript
const secrets = await vault.list();
console.log(secrets.secrets);
```

A secret is listed when at least the read threshold of guardians report holding
a share of it, because that is exactly the condition under which it can be
reconstructed. The version reported is the newest any guardian holds.

## Deleting Secrets

Delete a secret from all guardians:

```typescript
const deleteResult = await vault.delete("api-key");
console.log(deleteResult.ackCount); // guardians that dropped their share
```

Like a write, a delete that does not reach quorum throws a `QuorumError`: enough
guardians still hold a share to reconstruct the secret, so it is not gone.

## Gateway Proxy API

For clients that cannot connect directly to guardians, the gateway exposes V1 vault endpoints. The gateway performs Shamir splitting/combining server-side.

These endpoints are **not** protected by the namespace API key — the `/v1/vault/` path is public in the gateway's routing. Instead, each push and pull request must prove ownership of the identity with a fresh Ed25519 signature, verified independently by the gateway and by every guardian it forwards to. There is no SDK helper for the gateway proxy path; the caller is responsible for holding the Ed25519 identity keypair and signing the canonical message itself.

### Store via Gateway

The request body requires `identity` (64 hex chars, `= SHA-256(pubkey)`), the base64-encoded `envelope`, a monotonically increasing `version`, the hex-encoded `pubkey`, and a hex-encoded Ed25519 `signature` over the ASCII message `vault-push-v1:<identity>:<version>`.

```typescript
const message = `vault-push-v1:${identityHex}:${version}`;
const signature = sign(message, privateKey); // your Ed25519 signer, hex-encoded

const res = await fetch("https://ns-myapp.orama-devnet.network/v1/vault/push", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    identity: identityHex,
    envelope: base64EncryptedData,
    version,
    pubkey: pubkeyHex,
    signature,
  }),
});

const { status, ack_count, total, quorum, threshold } = await res.json();
```

A `409` response (`status: "version_conflict"`) means a quorum of guardians already has this version or newer — re-read and bump `version` before retrying.

### Retrieve via Gateway

The request body requires `identity`, `pubkey`, a `timestamp` (unix seconds, must be within 120 seconds of the gateway's clock), and a hex-encoded Ed25519 `signature` over the ASCII message `vault-pull-v1:<identity>:<timestamp>`.

```typescript
const timestamp = Math.floor(Date.now() / 1000);
const message = `vault-pull-v1:${identityHex}:${timestamp}`;
const signature = sign(message, privateKey);

const res = await fetch("https://ns-myapp.orama-devnet.network/v1/vault/pull", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    identity: identityHex,
    pubkey: pubkeyHex,
    signature,
    timestamp,
  }),
});

const { envelope, collected, threshold } = await res.json();
```

### Health Check

```bash
curl https://ns-myapp.orama-devnet.network/v1/vault/health
```

No authentication required. Returns aggregate guardian health: `healthy`, `degraded`, or `unavailable`.

### Rate Limits

| Operation | Limit |
|-----------|-------|

## REST API Reference

### Guardian V2 Endpoints (Direct)

Used by the SDK when connecting directly to guardian nodes.

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| POST | `/v2/vault/auth/challenge` | None | Request authentication challenge |
| POST | `/v2/vault/auth/session` | None | Exchange challenge response for session token |
| PUT | `/v2/vault/secrets/{name}` | Session | Store a named secret share |
| GET | `/v2/vault/secrets/{name}` | Session | Retrieve a named secret share |
| DELETE | `/v2/vault/secrets/{name}` | Session | Delete a named secret share |
| GET | `/v2/vault/secrets` | Session | List all secrets for identity |

Session tokens are passed via the `X-Session-Token` header. Sessions expire after 1 hour and are invalidated on guardian restart.

### Gateway V1 Endpoints (Proxy)

These paths are public in the gateway's routing — the namespace API key is not checked. Push and pull are instead authenticated per-request with an Ed25519 ownership signature (see [Gateway Proxy API](#gateway-proxy-api)).

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| POST | `/v1/vault/push` | Ed25519 ownership signature | Store secret (gateway splits into shares) |
| POST | `/v1/vault/pull` | Ed25519 ownership signature | Retrieve secret (gateway combines shares) |
| GET | `/v1/vault/health` | None | Aggregate guardian health |
| GET | `/v1/vault/status` | None | Guardian count, healthy count, threshold |

### Guardian Health Endpoints

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| GET | `/v1/vault/health` | None | Liveness check |
| GET | `/v1/vault/status` | None | Runtime config (data_dir, ports) |
| GET | `/v1/vault/guardians` | None | List known guardian nodes |

## Authentication

The direct V2 path issues session tokens:

1. Client requests a challenge from the guardian (`/v2/vault/auth/challenge`)
2. Guardian returns a nonce, a timestamp, and an HMAC tag over both computed
   with the guardian's own server secret
3. Client sends those three values back (`/v2/vault/auth/session`)
4. Guardian recomputes the tag with the same server secret and issues a session
   token, used for all subsequent requests via `X-Session-Token`

The client is cached per guardian and refreshed transparently when it expires.

**No client secret takes part in this exchange.** The guardian verifies a tag it
produced itself, so possession of an identity hash is all it takes to obtain a
session for that identity — which is why the SDK never had a use for the
`hmacKey` its configuration used to demand. The Ed25519 proof this needs is
tracked as bug-51/bug-52 and is the "Phase 3" the guardian's own source refers
to. Until then, a guardian's reachability on the WireGuard overlay is the real
boundary: treat anything on the mesh as able to read any identity's shares.

Requests through the gateway (`/v1/vault/push` and `/v1/vault/pull`) are a
different mechanism and do carry a real per-request Ed25519 ownership
signature.

### Session Lifecycle

| Property | Value |
|----------|-------|
| Expiry | 1 hour |
| Caching | Per-guardian, automatic |
| Invalidation | On guardian restart |
| Refresh | Automatic on 401 response |

## Threshold Configuration

The adaptive threshold is calculated automatically based on how many guardians you configure. You do not set it manually. The system determines:

- **Read threshold (K)** — `max(2, floor(N/3))`. The minimum number of shares needed to reconstruct the secret; any K−1 shares reveal nothing.
- **Write quorum (W)** — `min(N, max(K+1, ceil(2N/3)))`. The number of guardians that must acknowledge a write for it to succeed.

The invariant **W > K** is deliberate: a write is only reported successful once it has persisted strictly more shares than a read requires, so a successful write is always recoverable and survives losing at least one guardian.

| Guardians (N) | Read Threshold (K) | Write Quorum (W) |
|---------------|--------------------|------------------|
| 3 | 2 | 3 |
| 5 | 2 | 4 |
| 7 | 2 | 5 |
| 9 | 3 | 6 |
| 12 | 4 | 8 |

More guardians means higher fault tolerance. With three guardians, losing one still allows full reconstruction. Because W > K, a write reported successful is never left below the read threshold.

## Crypto Utilities

`@debros/orama-vault` exports the low-level cryptographic primitives it uses
internally. They were exported from `@debros/orama` until they moved with the
rest of the vault client:

```typescript
import {
  // Shamir's Secret Sharing
  shamirSplit,
  shamirCombine,

  // Symmetric encryption
  encrypt,
  decrypt,
  encryptString,
  decryptString,
  encryptAndSerialize,
  deserializeAndDecrypt,

  // Key management
  generateKey,
  generateNonce,
  clearKey,
  deriveKeyHKDF,

  // Serialization
  serializeEncrypted,
  deserializeEncrypted,
  encryptedToHex,
  encryptedFromHex,
  encryptedToBase64,
  encryptedFromBase64,

  // Validation
  isValidEncryptedData,
} from "@debros/orama-vault";
```

| Function | Description |
|----------|-------------|
| `shamirSplit` / `shamirCombine` | Split and reconstruct secrets using Shamir's Secret Sharing |
| `encrypt` / `decrypt` | Symmetric encryption primitives (AES) |
| `encryptString` / `decryptString` | String convenience wrappers |
| `encryptAndSerialize` / `deserializeAndDecrypt` | Encrypt + serialize in one step |
| `generateKey` / `generateNonce` | Cryptographic key and nonce generation |
| `clearKey` | Securely wipe a key from memory |
| `deriveKeyHKDF` | Derive keys using HKDF-SHA256 |
| `serializeEncrypted` / `deserializeEncrypted` | Binary serialization helpers |
| `encryptedToHex` / `encryptedFromHex` / `encryptedToBase64` / `encryptedFromBase64` | Encoding utilities |
| `isValidEncryptedData` | Validate encrypted data structure |

## Guardian Service

The `vault-guardian` binary runs on each node as a systemd service. It is written in Zig and compiled as part of the Orama build pipeline.

### CLI Flags

| Flag | Default | Description |
|------|---------|-------------|
| `--config` | `/opt/orama/.orama/data/vault/vault.yaml` | Path to config file |
| `--data-dir` | | Override data directory |
| `--port` | `7500` | Client API port |
| `--bind` | `0.0.0.0` | Bind address |
| `--version` | | Show version |

### Ports

| Port | Protocol | Description |
|------|----------|-------------|
| 7500 | HTTP | Client API (V1 + V2 endpoints) |
| 7501 | TCP (binary) | Peer protocol (heartbeat, share verification) |

### Peer Protocol

Guardians communicate with each other over a binary TCP protocol on port 7501 for health monitoring and share verification:

| Message | Description |
|---------|-------------|
| Heartbeat | Guardian announces health and share count |
| Heartbeat ACK | Peer acknowledges |
| Verify Request | Check if a peer has a specific share |
| Verify Response | Peer responds with share status |

## Access Control

Secrets are scoped to your identity. Each guardian authenticates requests via HMAC challenge-response, so only the identity that stored a secret can retrieve, list, or delete it. Different identities on the same guardian cluster have completely isolated secret namespaces.
