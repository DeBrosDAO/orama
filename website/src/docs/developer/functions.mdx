# Functions

Orama Functions lets you run serverless code on the decentralized network using WebAssembly (WASM). Write functions in Go, compile to WASM with TinyGo, and deploy them to execute on Orama nodes in a sandboxed wazero runtime with configurable memory limits and timeouts.

## Overview

Functions are written in Go, compiled to WASM using [TinyGo](https://tinygo.org/), and executed in an isolated wazero sandbox on Orama nodes. Each function receives JSON input via **stdin** and returns JSON output via **stdout**. Functions can access Orama platform services -- database, cache, HTTP, secrets, PubSub, WebSocket, and logging -- through **host functions** injected by the runtime.

Key characteristics:

- **Go + TinyGo** -- Write standard Go, compile to a portable WASM binary
- **Sandboxed execution** -- Each invocation runs in an isolated wazero instance with memory and timeout limits
- **Platform integration** -- Host functions provide direct access to RQLite, Olric, PubSub, WebSocket, secrets, and outbound HTTP
- **Event-driven** -- Functions can be invoked via HTTP, WebSocket, or triggered automatically by PubSub messages

## Writing Functions

### Project Structure

A function consists of two files:

```
my-function/
├── function.go      # Handler code (Go)
└── function.yaml    # Configuration
```

### function.yaml

The configuration file defines the function's name, resource limits, and environment variables.

```yaml
name: my-function       # Required. Letters, digits, hyphens, underscores.
public: false           # Allow unauthenticated invocation (default: false)
memory: 64              # Memory limit in MB (1-256, default: 64)
timeout: 30             # Execution timeout in seconds (1-60, default: 30)
retry:
  count: 0              # Retry attempts on failure (default: 0)
  delay: 5              # Seconds between retries (default: 5)
env:                    # Environment variables (accessible via get_env)
  MY_VAR: "value"
ws_auth: capability     # Optional. Also let the function's WebSocket be opened with a
                        # capability it minted, instead of a credential. Refused on an
                        # internal function. Empty (default): a credential only.
```

A private function (`public: false`) needs a wallet session, or an API key that holds the `invoke` grant; a storage-only key is rejected. A deploy whose memory or timeout is not a whole number, is below 1, or is above the gateway's maximum (256 MB, 60 s) is refused `400 VALIDATION_FAILED` naming the field. A direct invoke that exceeds its timeout returns `429 RATE_LIMITED` (retryable); `TIMEOUT` (504) appears only when the namespace-proxy budget is exceeded.

### function.go

The SDK provides a helper package that handles stdin/stdout boilerplate. When you scaffold a new function with `orama function init`, this is the generated template:

```go
package main

import "github.com/DeBrosOfficial/network/sdk/fn"

func main() {
	fn.Run(func(input []byte) ([]byte, error) {
		var req struct {
			Name string `json:"name"`
		}
		fn.ParseJSON(input, &req)
		if req.Name == "" {
			req.Name = "World"
		}
		return fn.JSON(map[string]string{
			"greeting": "Hello, " + req.Name + "!",
		})
	})
}
```

The `fn` package provides:

| Function | Description |
|----------|-------------|
| `fn.Run(handler)` | Reads input from stdin, calls the handler, writes output to stdout |
| `fn.JSON(v)` | Marshals a value to JSON bytes |
| `fn.ParseJSON(data, v)` | Unmarshals JSON bytes into a value |

You can also write functions without the SDK, reading from `os.Stdin` and writing to `os.Stdout` directly:

```go
package main

import (
    "encoding/json"
    "io"
    "os"
)

func main() {
    input, _ := io.ReadAll(os.Stdin)

    var payload struct {
        Name string `json:"name"`
    }
    json.Unmarshal(input, &payload)

    response := map[string]string{
        "message": "Hello, " + payload.Name + "!",
    }
    output, _ := json.Marshal(response)
    os.Stdout.Write(output)
}
```

### Building

> **`orama function deploy` reuses an existing `function.wasm`.** It builds only when `function.wasm` is absent. If you edit `function.go` but a stale `function.wasm` is still on disk, `deploy` uploads the **old** binary and your change silently never ships. After editing source run `orama function build` (which overwrites the wasm) or delete `function.wasm` first.

Functions are compiled to WASM using TinyGo:

```bash
# Using the CLI (recommended -- validates the output)
orama function build

# Build from a specific directory
orama function build ./my-function

# Or manually
tinygo build -o function.wasm -target wasi function.go
```

## Deployment

### CLI

```bash
# Scaffold a new function
orama function init my-function

# Build and deploy from the function directory
cd my-function
orama function build
orama function deploy

# Deploy from a specific directory
orama function deploy ./my-function
```

If no `function.wasm` file exists when you run `deploy`, it is built automatically.

Each deploy creates a new version. The WASM binary is stored on IPFS (content-addressed) and metadata is stored in RQLite.

### Where a function lives

A function belongs to the namespace of the credential that deploys it, and it is stored in and run by that namespace's own gateway, `https://ns-<namespace>.<domain>`. Point the CLI or your requests there.

Every management request — deploy, delete, enable and disable, get, versions, logs, list, triggers, secrets — acts on the credential's namespace. A request that names a different namespace, in the deploy metadata, the `namespace` form field, `?namespace=` or an `X-Namespace` header, is refused with 403.

A gateway runs only its own namespace's functions, and the cluster's main gateway is the `default` namespace's. A function request sent there for any other namespace is forwarded to that namespace's gateway: the namespace in `/v1/invoke/<namespace>/<name>` or `?namespace=`, otherwise the credential's. A credential of another namespace is refused, and an unauthenticated request that names no namespace is refused with a message pointing at the namespace gateway.

### REST API

Deploy by uploading a multipart form with the compiled WASM binary and configuration:

```bash
curl -X POST https://gateway.example.com/v1/functions \
  -H "Authorization: Bearer <token>" \
  -F "name=hello-world" \
  -F "is_public=false" \
  -F "memory_limit_mb=64" \
  -F "timeout_seconds=30" \
  -F "retry_count=0" \
  -F "retry_delay_seconds=5" \
  -F "wasm=@./function.wasm"
```

## Invocation

### SDK

The TypeScript SDK invokes functions via the `/v1/invoke/{namespace}/{name}` endpoint:

```typescript
import { createClient } from "@debros/orama";

const client = createClient({
  baseURL: "https://ns-myapp.cluster.example.com",
  apiKey: process.env.ORAMA_API_KEY,
  functionsConfig: {
    namespace: "my-namespace",
  },
});

interface GreetInput {
  name: string;
}

interface GreetOutput {
  greeting: string;
}

const result = await client.functions.invoke<GreetInput, GreetOutput>(
  "hello-world",
  { name: "World" }
);

console.log(result.greeting); // "Hello, World!"
```

### CLI

```bash
orama function invoke hello-world --data '{"name": "World"}'
```

The `--data` flag accepts a JSON string (defaults to `"{}"`).

### REST API

```bash
# Via the function-specific invoke endpoint
curl -X POST https://gateway.example.com/v1/functions/hello-world/invoke \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"name": "World"}'

# Via the direct invoke endpoint (used by the SDK)
curl -X POST https://gateway.example.com/v1/invoke/my-namespace/hello-world \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"name": "World"}'
```

A public function can be invoked without a credential, but the request has to name the namespace: `/v1/invoke/<namespace>/<name>`, or `/v1/functions/<name>/invoke?namespace=<namespace>`. With a credential and no namespace named, the credential's namespace is used.

A deployed app invokes functions with its own workload token ([Access control](/docs/developer/access-control#a-deployed-app-s-identity)). What it may run is its grant at the moment of the call, not the scopes its token was minted with, so narrowing or revoking the grant takes effect on a token already issued. An app holds nothing until `orama app grants set <app> runtime` gives it something; a `403 FORBIDDEN` means the grant does not cover the function, and `401` means no identity. It is never an admin on invoke, so admin-only `internal` functions stay closed to it, and its token is good in its own namespace only: a function of another namespace is refused `403`.

### WebSocket Invoke

Functions can also be invoked over WebSocket for streaming use cases:

```
WS /v1/functions/{name}/ws
```

You can also invoke a specific version by appending `@version` to the name (e.g., `hello-world@2`).

A socket is authorized at the upgrade and then held to the token that opened it: the gateway closes it with `4403` within 10 seconds of that token being revoked, and with `4401` two minutes after it expires. A persistent (`ws_persistent: true`) socket stays open across token rotation by sending `{"__orama":"auth.refresh","jwt":"<new token>"}` — for the same account the socket was opened with; a token for anyone else is refused.

A function that declares `ws_auth: capability` in function.yaml can also have its socket opened with a **capability** instead of a credential: `WS /v1/functions/{name}/ws?namespace=<ns>&cap=<token>`. The function mints one for its own socket with `capability_mint(resource, ttl_seconds)`, from a call made by a device-bound session, and hands it to whoever should be able to write to that resource. The gateway checks it before the upgrade, refuses it with a credential beside it, and closes the socket within 10 seconds of `capability_revoke(token)` or of the issuing device being revoked. The function reads what it grants with `get_caller_capability()` and sees no caller. No credential names the sender, but the gateway still sees the client's address, the timing, the resource and which capability was used.

## Host Functions API

Host functions let your WASM code interact with Orama platform services. They are available to every function without additional configuration.

### Module names and the ABI

Host functions use a pointer/length ABI for strings. They are registered under three module names that all resolve to the same table: `env` (canonical, matches the WASI and TinyGo convention and the `sdk/fn` package), `host` and `orama` (aliases kept indefinitely).

```go
//go:wasmimport env db_query_v2
```

If you see `failed to instantiate module: module[X] not instantiated`, your function imported from a name other than those three. Most functions written with the `sdk/fn` package never need a raw import.

### Context

| Function | Description |
|----------|-------------|
| `get_caller_wallet()` | The resolved caller: the JWT subject with bearer auth, else a namespace pseudo-id with an API key. |
| `get_caller_jwt_subject()` | The JWT `sub` claim explicitly. Empty when the request was not JWT-authenticated. Use it when binding on the JWT-signed identity matters. |
| `get_caller_device_id()` | The device the caller's session is bound to (the token's `did`): the RFC 7638 thumbprint of a key the device proved it holds. Empty for a session bound to no device, an API key, or no credential. |
| `get_caller_capability()` | What the capability the caller's socket was opened with grants, as JSON `{"cap_id","resource","issuer_device","expires_at"}`. Empty when the caller came in on a credential. |
| `get_caller_claim(name)` | A custom JWT claim by name. Empty if missing. |
| `get_request_id()` | The unique invocation ID. |
| `get_env(key)` | An environment variable from function.yaml. |
| `get_secret(name)` | A decrypted secret. See [Secrets Management](#secrets-management). |

### Database (RQLite)

Read and write the **namespace's own** database. Prefer the `_v2` forms: the legacy `db_execute` returns 0 for both "0 rows" and "SQL error".

| Function | Description |
|----------|-------------|
| `db_query_v2(sql, argsJSON)` | SELECT. Returns `{"rows": [...], "error": "...", "code": "..."}`, which distinguishes an empty result from a failure. |
| `db_execute_v2(sql, argsJSON)` | INSERT, UPDATE, DELETE. Returns `{"rows_affected", "last_insert_id", "error", "code"}`. |
| `db_query(sql, argsJSON)` | Legacy. Returns a JSON array of rows with no way to surface an error. |
| `db_execute(sql, argsJSON)` | Legacy. Returns the affected row count only. |
| `db_transaction(opsJSON)` | Atomic batch, below. |
| `db_query_batch`, `exec_and_publish` | Batched reads (with an optional `consistency` of `weak` or `none`), and a transaction plus a publish. |

A function's SQL runs through the same filter as the raw-database routes: see [What tenant SQL may not do](/docs/developer/databases#what-tenant-sql-may-not-do). A refusal is a failed host call: `db_query_v2` and `db_execute_v2` return `0`.

**Transactions.** `db_transaction` takes `{"ops": [{"kind": "exec"|"query", "sql": "...", "args": [...]}, ...]}` and returns `{"results": [...], "committed": bool, "failed_index": n, "error": "", "code": ""}`. **Always check `committed`.** Any failing `exec` rolls back the whole batch; `query` ops run after the `exec` batch commits and see its writes. Result order matches input order. The limit that bites in practice is **100 statements per batch**: a write whose size scales with fan-out (one row per participant) fails deterministically at 101, so chunk work into batches of 100 or fewer.

| `code` | Meaning | Retry? |
|---|---|---|
| `CONSTRAINT_VIOLATION` | UNIQUE, PRIMARY KEY, NOT NULL, CHECK or FOREIGN KEY violated | No |
| `TOO_MANY_STATEMENTS` | Over the per-batch cap | No: split the batch |
| `PAYLOAD_TOO_LARGE` | Result rows or bytes over the caps (10,000 rows per query op, 32 MiB per batch) | No: paginate |
| `DEADLINE_EXCEEDED` | The call ran past its deadline (10 s for `db_query_batch`) | Yes |
| `UNAVAILABLE` | Database unreachable, or the leader was lost mid-call | Yes |
| `INVALID_ARGUMENT` | Malformed request | No |
| `INTERNAL` | Anything else SQLite rejects (missing table, syntax error) | Depends |

### Cache (Olric)

Read and write to the distributed Olric cache. Each namespace has its own cache: a function reads and writes only its namespace's keys.

| Function | Description |
|----------|-------------|
| `cache_get(key)` | Get cached value by key. Returns empty on miss. |
| `cache_set(key, value, ttlSeconds)` | Store value. `ttlSeconds > 0` expires the entry after that long (at most 10 years); `0` means no expiry; a negative or longer ttl is refused. No return value; a failure is logged by the gateway. |
| `cache_delete(key)` | Remove a key. Returns 1 when the key is gone afterwards (including when it was never set), 0 on failure. Requires gateway 0.200.0 or later: a function that imports it fails to instantiate on an older gateway. |
| `cache_incr(key)` | Atomically increment by 1 (initializes to 0 if missing). |
| `cache_incr_by(key, delta)` | Atomically increment by delta. |

### Storage (IPFS)

There is no `storage_put` or `storage_get` host function: a function cannot pin or read IPFS directly, and a function that imports them fails to instantiate. Storage endpoints need a logged-in user (an API key alone is refused), so the usual pattern is that the **client** uploads with its own session and passes the CID to a function. One storage host function exists, for [relayed fetch](/docs/privacy/relayed-fetch):

| Function | Description |
|----------|-------------|
| `storage_fetch_cap_mint(...)` | Mint fetch capabilities for a canonical CID, for a function that wants to hand someone an identity-free download. Does not check ownership or a storage selector. |

### HTTP and anonymous HTTP

| Function | Description |
|----------|-------------|
| `http_fetch(method, url, headersJSON, body)` | Outbound HTTP. Returns `{"status", "headers", "body"}`. 30 s timeout. The destination is checked **on the socket**, for every resolved address and every redirect: loopback, private, link-local, carrier-grade NAT, multicast and the IPv6 forms that wrap IPv4 are refused, so a hostname that resolves to an internal address cannot reach node-local services. |
| `anon_fetch(method, url, headersJSON, body)` | `http_fetch` through the node's Tor client: the destination sees a Tor exit, not the gateway. There is no direct path. |
| `anyone_fetch(...)` | Deprecated alias of `anon_fetch`, kept because shipped functions import it. |

### PubSub

| Function | Description |
|----------|-------------|
| `pubsub_publish(topic, dataJSON)` | Publish to a topic. Returns true on success. Topics under `_orama/` are reserved. |
| `ws_pubsub_bridge(clientID, topic)`, `ws_pubsub_unbridge` | Forward every message on a topic to a function WebSocket client without invoking the function per message. `_orama` JSON keys are reserved; a function that passes user input as the topic exposes every room's membership to that user, so fix the topic in the function. Open the socket with `?pubsub_delivery=stamped` to receive `{"_orama":"pubsub.message","topic":...,"data_base64":...}` envelopes. |

### Push

| Function | Description |
|----------|-------------|
| `push_send(userID, msgJSON)` | Push to every device the user registered in this namespace. 1 or 0. |
| `push_send_v2(userID, msgJSON)` | Same, returning a JSON envelope with a result per device. |
| `push_send_topic(topicID, msgJSON)` | Push to a rotating push topic. |

See [Push notifications](/docs/developer/push).

### WebRTC

| Function | Description |
|----------|-------------|
| `webrtc_admit(room, user, device, ttl_seconds)` | Admit a user to a room (when the namespace requires admission). |
| `webrtc_kick(room, user)` | Revoke admissions and remove connections. |
| `webrtc_mute(room, user, muted)` | Stop forwarding a user's audio. |

See [WebRTC](/docs/developer/webrtc#identity-admission-and-moderation). TURN credentials are available to a function through a host function of their own with a 24 hour lifetime.

### Capabilities

| Function | Description |
|----------|-------------|
| `capability_mint(...)` | Mint a capability that opens this function's WebSocket without a credential (needs `ws_auth: capability` in `function.yaml` and a device-bound session). |
| `capability_revoke(token)` | Revoke one. |

See [Access control](/docs/developer/access-control#capabilities-access-without-an-identity).

### Ephemeral state

Short-lived per-subscriber state (typing indicators, presence, call ringing, live cursors) that the gateway **auto-clears the moment the owning WebSocket client disconnects**: no heartbeats, no prune crons. It also expires on a TTL backstop (default 60 s, maximum 30 minutes). The owner and namespace come from the server-trusted invocation context and cannot be spoofed.

| Function | Description |
|----------|-------------|
| `ephemeral_state_set(topic, key, payload, ttlMs)` | Record state owned by the current invocation's WebSocket client and publish an `ephemeral.set` event on the topic. 1 on success; 0 if there is no WebSocket client, an empty topic or key, a payload over 16 KiB, or more than 256 keys for the client. `ttlMs` is an i64. |
| `ephemeral_state_clear(topic, key)` | Clear state this client owns; publishes `ephemeral.clear` with reason `explicit`. Idempotent. |
| `ephemeral_state_list(topic)` | Reconnect catch-up read: a JSON envelope `{"entries":[{"key","client_id","payload","expires_in_ms"}]}`. Works without a WebSocket client. |

Subscribers see events on the same topic, tagged with the `_orama` discriminator, with a `reason` of `explicit`, `disconnect` (the zero-lag path) or `expired`.

### WebSocket

Send messages to WebSocket clients (only available when the function is invoked via WebSocket).

| Function | Description |
|----------|-------------|
| `ws_send(clientID, data)` | Send data to a specific WebSocket client. |
| `ws_broadcast(topic, data)` | Broadcast data to all WebSocket clients on a topic. |

### Logging

Structured logging captured in invocation logs.

| Function | Description |
|----------|-------------|
| `log_info(message)` | Log an info-level message. |
| `log_error(message)` | Log an error-level message. |

## Secrets Management

Secrets are encrypted at rest (AES-256-GCM) and scoped to your namespace. Functions read them at runtime via `get_secret("name")`.

### Setting Secrets

```bash
# Set a secret (inline value)
orama function secrets set APNS_KEY_ID "ABC123DEF"

# Set a secret from a file (useful for PEM keys, certificates)
orama function secrets set APNS_AUTH_KEY --from-file ./AuthKey_ABC123.p8

# List all secret names (values are never shown)
orama function secrets list

# Delete a secret
orama function secrets delete APNS_KEY_ID

# Delete without confirmation
orama function secrets delete APNS_KEY_ID --force
```

### Secrets via REST API

```bash
# Set a secret
curl -X PUT https://gateway.example.com/v1/functions/secrets \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"name": "MY_SECRET", "value": "secret-value"}'

# List secret names
curl https://gateway.example.com/v1/functions/secrets \
  -H "Authorization: Bearer <token>"

# Delete a secret
curl -X DELETE https://gateway.example.com/v1/functions/secrets/MY_SECRET \
  -H "Authorization: Bearer <token>"
```

### How It Works

1. **You set secrets** via the CLI or API -- they are encrypted and stored in the database
2. **Functions read secrets** at runtime via `get_secret("name")` -- decrypted on demand
3. **Namespace isolation** -- each namespace has its own secret store; functions in namespace A cannot read secrets from namespace B

## PubSub Triggers

Triggers let functions react to events automatically. When a message is published to a PubSub topic, all functions with a trigger on that topic are invoked asynchronously.

### Managing Triggers

```bash
# Add a trigger: invoke "my-function" when messages hit "events:incoming"
orama function triggers add my-function --topic events:incoming

# List triggers for a function
orama function triggers list my-function

# Delete a trigger
orama function triggers delete my-function <trigger-id>
```

### Triggers via REST API

```bash
# Add a trigger
curl -X POST https://gateway.example.com/v1/functions/my-function/triggers \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"topic": "events:incoming"}'

# List triggers
curl https://gateway.example.com/v1/functions/my-function/triggers \
  -H "Authorization: Bearer <token>"

# Delete a trigger
curl -X DELETE https://gateway.example.com/v1/functions/my-function/triggers/<id> \
  -H "Authorization: Bearer <token>"
```

### Trigger Event Payload

When triggered via PubSub, the function receives this JSON via stdin:

```json
{
  "topic": "events:incoming",
  "data": { "key": "value" },
  "namespace": "my-namespace",
  "trigger_depth": 1,
  "timestamp": 1708972800
}
```

### Depth Limiting

To prevent infinite loops (function A publishes to a topic that triggers function A again), trigger depth is tracked. The maximum depth is **5**. If a function's output triggers another function, `trigger_depth` increments. At depth 5, no further triggers fire.
