# Sandbox clusters

Spin up a temporary five-node Orama cluster on Hetzner Cloud for development and testing. Cost depends on the server type you pick: a few euro cents per hour for a small shared-vCPU cluster.

```bash
orama maint sandbox setup                       # one-time: API key, domain, floating IPs, SSH key
orama maint sandbox create --name my-feature    # ~5 minutes
orama maint sandbox status
orama maint sandbox ssh 1
orama maint sandbox rollout                     # deploy code changes
orama maint sandbox destroy
```

## Prerequisites

1. **A Hetzner Cloud project** with an API token that has read and write permission (Security, API Tokens).
2. **A domain or subdomain whose nameservers are two Hetzner Floating IPs.** For `sbx.example.com`, create glue records `ns1.sbx.example.com` and `ns2.sbx.example.com` pointing at the floating IPs, and set those as the domain's nameservers. Propagation can take up to 48 hours. `orama maint sandbox setup` guides you through it and can verify the glue.
3. **A signed archive and RootWallet.** `create` and `rollout` take `--archive <path>` (what `orama maint build` printed) or build this checkout. Either way the archive must be signed by the RootWallet account unlocked when you run them; that account is the only signer a sandbox trusts. An archive signed by anyone else, or unsigned, is refused before any server is created.

## `orama maint sandbox setup`

An interactive wizard: validates your Hetzner token; asks for the sandbox domain; lets you pick a datacenter (default `nbg1`) and a server type with prices (default the cheapest); creates or reuses two floating IPs (about EUR 0.005 an hour each); creates a firewall with sandbox rules; creates a RootWallet SSH entry (`sandbox/root`) and uploads its public key to Hetzner; and shows the DNS instructions. Config is saved to `~/.orama/sandbox.yaml`.

## Commands

| Command | What it does |
|---|---|
| `create [--name <name>] [--archive <path>]` | Creates a five-node cluster. Without `--name` a random one is generated. A name is lowercase letters, digits and `-`, at most 40 characters |
| `destroy [--name] [--force]` | Unassigns floating IPs, deletes all five servers, removes the state file and pinned host keys |
| `list` | Lists sandboxes and checks Hetzner for orphaned servers with no state file |
| `status [--name]` | Per-node service status, RQLite role, commit index and voter count |
| `rollout [--name] [--archive <path>]` | Builds or takes an archive, pushes it, and rolling-upgrades followers first, leader last, with 15 seconds between nodes |
| `ssh <1-5>` | Interactive SSH into a node |
| `reset` | Deletes all sandbox infrastructure and config to start fresh |

### What `create` does

Layout: nodes 1 and 2 are nameservers (CoreDNS, Caddy and all services); nodes 3 to 5 are regular nodes.

1. Provision five servers (parallel, about 90 s), pinning each server's SSH host key as soon as its sshd answers.
2. Assign floating IPs to the nameserver nodes.
3. Put the verified archive on every server the way `orama node setup` does: verified on your machine, uploaded as a canonical re-pack, staged by `orama maint node stage-archive`, which creates the server's trust anchor from your wallet.
4. Install the genesis node with `--operator-wallet <your wallet>` and `--acme-ca letsencrypt-staging`, and wait until it serves a TLS certificate for the sandbox domain (each invite pins it).
5. Join the other four nodes one at a time with health checks, each with an invite minted on genesis just before use and `--expect-archive-signers <your wallet>`.
6. Verify cluster health.

**One sandbox at a time.** The floating IPs are shared, so only one sandbox can own the nameservers. Destroy the active one before creating another.

A sandbox created before host keys were pinned has no `~/.orama/sandboxes/<name>.known_hosts` and is refused for rollout; destroy it and create a new one.

## Running the cluster guide against a sandbox

The cluster guide e2e ([Testing](/docs/contributor/testing#the-cluster-guide-e2e)) can run its plan against a sandbox.

## Cost and troubleshooting

You pay for the servers while they exist and for the floating IPs while they are reserved. Always `destroy` when done. `orama maint sandbox list` shows orphans. If `create` stalls, a pending approval prompt in the RootWallet app is the usual cause; `orama maint sandbox` reports how many prompts are waiting.
