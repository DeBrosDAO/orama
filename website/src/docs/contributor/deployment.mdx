# Release and rollout

How code gets from a checkout onto nodes. For installing a cluster the first time see [Install a cluster from scratch](/docs/operator/install-from-scratch); for the full upgrade protocol see [Upgrades](/docs/operator/upgrades). This page is the contributor's view.

## The model

Nodes never compile. You build one **signed archive** on your computer and every node unpacks it. A new version is a new archive and a **rolling restart**: extract can be parallel, restarts are serial, with a health gate between nodes.

## The commands

```bash
cd core
orama build                                     # signed archive; prints its path
orama push --env <env> --archive <path>         # upload and verify on every node, restart nothing
orama node upgrade --env <env>                  # read every node's state, print the plan
orama node upgrade --env <env> --yes            # execute it
orama rollout --env <env> --yes                 # build + push + upgrade in one
orama rollout --env <env> --no-build --archive <path> --yes
```

RootWallet must be open and unlocked for the whole run. The first run after a rebuild asks you to approve the new `orama` binary once (approval is keyed on the binary's hash).

## Reproducible builds

Two `orama build` runs of one commit produce the same archive byte for byte, so the people who sign a release can each rebuild it and compare hashes before they sign. A release build sets the date from the commit: `export SOURCE_DATE_EPOCH=$(git log -1 --format=%ct)`. Go binaries are built with `-trimpath`, `-buildvcs=false`, a stripped linker and `-mod=readonly`. The third-party programs (Olric, IPFS Cluster, Caddy) are built from modules checked in to the repository, each with a `go.sum`, and CoreDNS, Kubo and RQLite are refused unless they match a pinned commit or SHA-256. The archive lists its entries in a fixed order with fixed owners, modes and times. A change to a pinned program means changing its version constant and its module together; a test holds the two. CI builds each published release's archive twice per architecture, fails if the two differ, and attaches the archive and its SHA-256 to the release. CI holds no signing key.

## Releases, TUF and auto-update

A release is trusted when the DeBros **TUF release root** has signed the metadata that names its hash, and it needs no wallet signature on any node. All release keys are in the owner's RootWallet: one release key, listed in the root for the root, timestamp, snapshot and targets roles at threshold 1. Every signature is a human approval in the RootWallet desktop app, so a release is a short session at the owner's machine.

- The root is adopted on a node by setup (the network's manifest pins its SHA-256 and the CLI embeds it), with `orama node trust add-root`, or by an archive built with `orama build --release-root <root.json>`. Nothing fetches a root by itself. After that the root rotates through numbered files (`2.root.json`, `3.root.json`), each signed by the previous root's keys, which every node follows.
- The repository is a static HTTPS site, `https://releases.orama.network/`: the metadata is served as files and `targets/<path>` answers 302 to a GitHub release asset of `DeBrosDAO/orama`. A channel is a path prefix in the one targets file: `nightly/` (stagenet), `main/` (the future testnet) and `dev/<branch>/`. A client refuses metadata signed under another root or below a threshold, an expired timestamp, a snapshot older than the newest one it has accepted (rollback protection), and a target whose bytes differ.
- Every node runs `orama-autoupdate.timer`, which does nothing until the cluster stored a release repository and the node adopted a root. The cluster settings `auto-update` (`off`, `notify` by default, `auto`), `update-channel`, `update-window` and `release-repo` set the policy. With `auto` inside the window, nodes install the newest verified release one at a time under a cluster lock, behind the same health gate as a manual rolling upgrade; if the upgrade or the gate fails, the node puts the previous release back and the release is marked bad for the whole cluster, which stops the rollout.
- A machine that runs the chain is never `auto`. Its binary and verifier go in through `orama global stage-oramad --upgrade <plan>`.
- Auto-update installs only what the release root's key signed; it never signs anything.

### Cutting a release (maintainers)

Build the archive unsigned, from a clean checkout, with the global layer (`orama build --unsigned`, amd64 and arm64 if both are needed), then:

```bash
# once: the repository's root. Prints the digest network manifests pin.
orama maint release init-root --dir ~/.orama/release-repo

# each release: list the archives on a channel and sign (3 approvals)
orama maint release cut --channel nightly \
  --archive /tmp/orama-0.3.1-linux-amd64.tar.gz --dir ~/.orama/release-repo
orama maint release cut --channel nightly --archive ... --dry-run   # plan only: signs and writes nothing

# upload: archives to the GitHub release, then metadata to the host, timestamp last
orama maint release publish --dir ~/.orama/release-repo

# keep a quiet repository believed: every 7 days (nightly, dev) or 30 (main)
orama maint release refresh-timestamp --channel nightly --dir ~/.orama/release-repo
orama maint release publish --dir ~/.orama/release-repo

# before the root's year is up
orama maint release renew-root --dir ~/.orama/release-repo
```

`cut` says what each approval is for before it asks: the targets file (which archives, which channel), the snapshot that names it, and the timestamp that names the snapshot. It writes only to `--dir`, checks that a client would accept the result before it writes, and keeps the newest three versions of the channel (`--retention`; the RootWallet agent signs at most 200 targets). A version must be dotted numeric and newer than the channel's newest; a published version is immutable (`--replace` is for a `dev/<branch>` build that reuses one). A second `cut` before `publish` is refused; `publish` can be run again if it stopped part way. It refuses an archive that is wallet-signed, names signers or a root, or lacks the global layer on amd64 (`--allow-cluster-only`). `publish` needs `gh` logged in with upload rights on `DeBrosDAO/orama` and ssh to the release host (`--github-repo`, `--metadata-dest`); `--dry-run` prints the commands. The release host serves `/opt/orama-releases` with `website/deploy/releases.orama.network.nginx.conf`, installed once like the site's own.

The timestamp is the freeze protection: nodes refuse metadata whose timestamp has expired, so skipping a refresh stops releases for every node on the channel.

See [Upgrades](/docs/operator/upgrades#automatic-updates) and [Build and sign](/docs/operator/build-and-sign).

## Versions and releases

`VERSION` at the repository root is the single version. `make -C core bump VER=<x.y.z>` updates it everywhere; a release tag `v<version>` must match it or the release workflow fails. GoReleaser builds the CLI and node binaries for GitHub releases, Homebrew (stable only) and apt packages. The signed **install archive** that nodes use is built from a checkout with `orama build`, signed by your own wallet. CI also attaches an unsigned, reproducible archive to each release; it becomes installable through the TUF path above, not by being attached.

## Before rolling out

- Unit tests and `make test` (including the coverage gate) pass.
- Docs updated for any behaviour change, in the same change.
- If the change touches inter-node coordination, secrets, namespaces or deployments, read the upgrade page's **mixed-version windows**: pause namespace and deployment create and delete during the roll, and do not add a node until every cluster you are upgrading is on the same version.
- If the change adds a migration, it must be applied before the gateway that requires it starts; migrations take a cluster-wide lock, and the gateway refuses to start if its required schema is not applied (`orama node schema status`).
- RQLite v10 is one way. Take a registry backup first.

## Verification between nodes

```bash
orama monitor report --env <env> --node <ip>     # that node: services, RQLite state, WireGuard peers
orama monitor report --env <env>                 # the cluster: leader stable, quorum ok, mesh ok, indices in sync
```

Proceed only when both pass. `orama rollout` gates on the same signals itself and stops the moment a node fails to rejoin.

## What not to do

- Do not stop all nodes, replace binaries, then start all nodes.
- Do not run `orama node upgrade --restart` on several nodes in parallel.
- Do not clear RQLite data directories unless you are rebuilding the whole cluster.
- Do not stop `orama-node` on several nodes at once; it takes the index services with it.
- Do not fix a node by hand. Fix in source, test, then roll out.

## Environments

An environment is just a name for a cluster in your CLI. Promotion is rolling the same archive to the next one (`orama push --env <next> --archive <same path>`), which the nodes verify against their own trust anchor. Pushing the same archive to several clusters works only if each trusts the signer.
