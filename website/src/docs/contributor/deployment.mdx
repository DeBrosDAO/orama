# Release and rollout

How code gets from a checkout onto nodes. For installing a cluster the first time see [Install a cluster from scratch](/docs/operator/install-from-scratch); for the full upgrade protocol see [Upgrades](/docs/operator/upgrades). This page is the contributor's view.

## The model

Nodes never compile. You build one **signed archive** on your computer and every node unpacks it. A new version is a new archive and a **rolling restart**: extract can be parallel, restarts are serial, with a health gate between nodes.

## The commands

```bash
cd core
orama build                                     # signed archive; prints its path
orama push --env <env> --archive <path>         # upload and verify on every node, restart nothing
orama node upgrade --env <env>                  # read every node's state, print the plan
orama node upgrade --env <env> --yes            # execute it
orama rollout --env <env> --yes                 # build + push + upgrade in one
orama rollout --env <env> --no-build --archive <path> --yes
```

RootWallet must be open and unlocked for the whole run. The first run after a rebuild asks you to approve the new `orama` binary once (approval is keyed on the binary's hash).

## Versions and releases

`VERSION` at the repository root is the single version. `make -C core bump VER=<x.y.z>` updates it everywhere; a release tag `v<version>` must match it or the release workflow fails. GoReleaser builds the CLI and node binaries for GitHub releases, Homebrew (stable only) and apt packages. The signed **install archive** that nodes use is not a release artifact: you build it from a checkout with `orama build`, signed by your own wallet.

## Before rolling out

- Unit tests and `make test` (including the coverage gate) pass.
- Docs updated for any behaviour change, in the same change.
- If the change touches inter-node coordination, secrets, namespaces or deployments, read the upgrade page's **mixed-version windows**: pause namespace and deployment create and delete during the roll, and do not add a node until every cluster you are upgrading is on the same version.
- If the change adds a migration, it must be applied before the gateway that requires it starts; migrations take a cluster-wide lock, and the gateway refuses to start if its required schema is not applied (`orama node schema status`).
- RQLite v10 is one way. Take a registry backup first.

## Verification between nodes

```bash
orama monitor report --env <env> --node <ip>     # that node: services, RQLite state, WireGuard peers
orama monitor report --env <env>                 # the cluster: leader stable, quorum ok, mesh ok, indices in sync
```

Proceed only when both pass. `orama rollout` gates on the same signals itself and stops the moment a node fails to rejoin.

## What not to do

- Do not stop all nodes, replace binaries, then start all nodes.
- Do not run `orama node upgrade --restart` on several nodes in parallel.
- Do not clear RQLite data directories unless you are rebuilding the whole cluster.
- Do not stop `orama-node` on several nodes at once; it takes the index services with it.
- Do not fix a node by hand. Fix in source, test, then roll out.

## Environments

An environment is just a name for a cluster in your CLI. Promotion is rolling the same archive to the next one (`orama push --env <next> --archive <same path>`), which the nodes verify against their own trust anchor. Pushing the same archive to several clusters works only if each trusts the signer.

## Test clusters

[Sandbox clusters](/docs/contributor/sandbox) create five Hetzner servers, install the archive and give you a throwaway cluster. For release confidence the owner runs the fleet suite ([Testing](/docs/contributor/testing#fleet-e2e-the-release-gate)).
